# Reflected XSS in /util/serverStatusCheckService.jsp HostName parameter

**ID:** vuln-0001
**Severity:** MEDIUM
**Found:** 2026-09-20 21:41:12 UTC
**Target:** http://demo.testfire.net
**Endpoint:** /util/serverStatusCheckService.jsp
**Method:** GET
**CWE:** CWE-79
**CVSS:** 6.1
**Confidence:** High
**Fix Effort:** Trivial

## Description

The `HostName` query parameter of `/util/serverStatusCheckService.jsp` is written directly into an HTML response with no output encoding. Because the response is served with `Content-Type: text/html`, an attacker-supplied value containing markup is rendered and executed by the victim's browser, enabling reflected cross-site scripting on an unauthenticated endpoint.

## Evidence

HTTP response showing the injected markup reflected unescaped and served as HTML:

```http
GET /util/serverStatusCheckService.jsp?HostName=%3Cscript%3Ealert(document.domain)%3C%2Fscript%3E HTTP/1.1
Host: demo.testfire.net

HTTP/1.1 200 OK
Server: Apache-Coyote/1.1
Content-Type: text/html;charset=ISO-8859-1
Content-Length: 81

{
	"HostName": "<script>alert(document.domain)</script>",
	"HostStatus": "OK"
}
```

Browser execution of the proof payload (`window.__xss_pwned` and `document.title` are read back after the page is rendered):

```text
open  http://demo.testfire.net/util/serverStatusCheckService.jsp?HostName=%3Cscript%3Ewindow.__xss_pwned=1337%3Bdocument.title='XSS'%3C/script%3E
eval  window.__xss_pwned   -> 1337
eval  document.title       -> "XSS"
```

The parameter is reflected identically for every value, with no output encoding applied; the response content type is `text/html` and no CSP or `X-Content-Type-Options` header is present.

## Impact

An attacker who induces a victim to open a crafted link executes arbitrary JavaScript in the origin of the application. This permits theft of the victim's authenticated session material (the `JSESSIONID` and the non-HttpOnly `AltoroAccounts` cookie), manipulation of page content, forced state-changing requests in the victim's authenticated context, and credential/one-time-code phishing. No authentication is required to deliver the payload, and the endpoint is directly reachable over the network.

## Counterevidence

A pre-filing control review was performed and no blocking control is present on this path: the value is not passed through any encoder, the response is served as `text/html`, and neither `Content-Security-Policy` nor `X-Content-Type-Options` is returned. Execution was confirmed in a real browser engine rather than inferred from source alone, and a benign value (a plain hostname) is reflected in the same position, confirming the reflection point is the injected context and not a dead/broken endpoint. The application ships an HTML encoder (`ServletUtil.sanitizeWeb`) but it is not invoked here, so the existence of that helper does not neutralize this sink. The only residual doubt at the exploitation level is the need for victim link interaction (a standard reflected-XSS precondition), which is reflected in the CVSS user-interaction metric rather than treated as a blocker.

## What Would Change This Severity

If the endpoint were changed to serve `application/json` (so browsers no longer parse it as HTML) or a `Content-Security-Policy` blocking inline script were applied, exploitability would drop to informational; conversely, if analysis showed the reflected value were persisted and shown to other users, this would escalate to stored XSS and a higher severity.

## Technical Analysis

The endpoint is implemented as a four-line JSP scriptlet that interpolates the raw request parameter into a JSON-shaped body and returns it as HTML. The source is:

```jsp title=WebContent/util/serverStatusCheckService.jsp startLineNumber=1 endLineNumber=6
<%@ page language="java" contentType="text/html; charset=ISO-8859-1" pageEncoding="ISO-8859-1"%>

{
	"HostName": "<%=request.getParameter("HostName")%>",
	"HostStatus": "OK"
}
```

The scriptlet expression `<%=request.getParameter("HostName")%>` emits the value verbatim; no call to the application's own encoder (`ServletUtil.sanitizeWeb`, which wraps `StringEscapeUtils.escapeHtml`) is made. The page directive sets `contentType="text/html"`, so the browser parses the reflected value as HTML. A `<script>` element in the parameter therefore executes. The response carries no `Content-Security-Policy` and no `X-Content-Type-Options` header, and the reflection occurs outside any quoting that would neutralize markup.

## Proof of Concept

1. Craft a URL that injects a script element into the `HostName` parameter.
2. Send the request (or deliver the URL to a victim) and observe that the value is reflected verbatim in the response body, which is served as `text/html`.
3. In a browser, the injected script executes in the application origin: a proof payload that sets `window.__xss_pwned = 1337` and rewrites `document.title` confirms execution.
4. Confirm by reading back `window.__xss_pwned` and `document.title` from the rendered page.

````python
import requests

TARGET = "http://demo.testfire.net/util/serverStatusCheckService.jsp"
payload = "<script>window.__xss_pwned=1337;document.title='XSS'</script>"

r = requests.get(TARGET, params={"HostName": payload}, timeout=15)
print("HTTP", r.status_code)
print("Content-Type:", r.headers.get("Content-Type"))
print("--- body ---")
print(r.text)
# The injected <script> appears unescaped in a text/html response:
# {
#   "HostName": "<script>window.__xss_pwned=1337;document.title='XSS'</script>",
#   "HostStatus": "OK"
# }
```

Browser confirmation (URL-decoded payload shown for clarity):

```text
http://demo.testfire.net/util/serverStatusCheckService.jsp?HostName=<script>window.__xss_pwned=1337;document.title='XSS'</script>
```

URL-encoded form used for delivery:

```text
http://demo.testfire.net/util/serverStatusCheckService.jsp?HostName=%3Cscript%3Ewindow.__xss_pwned=1337%3Bdocument.title%3D%27XSS%27%3C%2Fscript%3E
````

## Code Analysis

**Location 1:** `WebContent/util/serverStatusCheckService.jsp` (line 4)
  Encode the reflected HostName value with the application's existing HTML encoder
  ```
  	"HostName": "<%=request.getParameter("HostName")%>",
  ```

  **Suggested Fix:**
```diff
- 	"HostName": "<%=request.getParameter("HostName")%>",
+ 	"HostName": "<%= com.ibm.security.appscan.altoromutual.util.ServletUtil.sanitizeWeb(request.getParameter("HostName")) %>",
```

## Remediation

1. HTML-encode the `HostName` value before it is written into the response, using the application's existing encoder `ServletUtil.sanitizeWeb` (backed by `StringEscapeUtils.escapeHtml`) rather than the weaker regex-based `sanitzieHtmlWithRegex`.
2. Correct the response type: a JSON payload should be served as `application/json`, not `text/html`. This removes the browser's HTML parsing context for the response and is the appropriate fix for the endpoint's actual purpose.
3. Add a restrictive `Content-Security-Policy` (for example `default-src 'none'; frame-ancestors 'none'`) and `X-Content-Type-Options: nosniff` at the application or container level as defense in depth.
4. Apply the same server-side output encoding to all other locations that reflect user input (for example the feedback confirmation pages) and prefer the framework's implicit escaping over raw scriptlet output.

## Fix Verification

Security closure: the patched line passes the reflected value through `ServletUtil.sanitizeWeb`, which is `StringEscapeUtils.escapeHtml(data)` (defined in `src/com/ibm/security/appscan/altoromutual/util/ServletUtil.java`, line 245). That converts `<`, `>`, `"`, and `&` to entities, so the `<script>` element in the input is delivered as inert text and cannot open a script context; the source-to-sink reflection is therefore closed.

Bypass review: I checked the sibling reflection points that handle the same class of input. `WebContent/feedbacksuccess.jsp` and `WebContent/index.jsp` already route values through `ServletUtil.sanitzieHtmlWithRegex`, whereas this JSP applies no filter at all, so this is the unguarded instance rather than a safe sibling. I confirmed the fix targets the raw scriptlet output specifically. I used `sanitizeWeb` (proper entity encoding) rather than the regex blacklist `sanitzieHtmlWithRegex`, because the regex approach is trivially bypassable (alternate encodings, unlisted handlers) and would not constitute a complete fix.

Preserved behavior: the endpoint's contract is unchanged for legitimate input — a normal hostname such as `127.0.0.1` contains no escapable characters and is echoed byte-for-byte, so the JSON shape, the `HostStatus` field, and the existing client-side JavaScript that reads `HostName` continue to work. Only values containing HTML metacharacters change, which is the intended effect.

Repository checks: not executed. This is a Java/JSP web application whose build/deploy pipeline is not available in the assessment environment and the finding was confirmed against the remote deployed instance, so I could not compile or redeploy the patched JSP to re-run the proof of concept. This gate is a gap: the patch was validated by tracing the encoder's behavior and the JSP expression syntax, not by rebuilding and re-testing the application. The one-line change is limited to a single scriptlet expression and introduces no new imports or symbols beyond an already-defined public static method.

## Assumptions

Exploitation requires the victim to open a crafted link (reflected XSS). No authentication is required to reach the endpoint, and the payload executes in the origin of the application, so any authenticated session cookie of a logged-in victim is reachable.
